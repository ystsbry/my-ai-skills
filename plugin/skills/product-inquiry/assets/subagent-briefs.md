# サブエージェントの役割・起動・ブリーフ（product-inquiry）

ホストが仮説ボードを所有し、サブエージェントは観測だけを返す。この分担を守るための役割表・起動手順・ブリーフ固定文・返答フォーマットをまとめる。起動の細部（エラー時の扱い、`blocked` の対応、後方互換）は herdr-subagent スキルに従う。

プロダクト探究のサブエージェントは **既にある証拠を漏れなく読む** 役に限る。ユーザーにインタビューしたり、ユーザーの反応を推測したりはさせない。

## 役割表

| 役割 | タブ名 | 使う場面 | 盲検（渡さないもの） | kind | モデル | effort | タイムアウト目安 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 事実棚卸し | `pi-<テーマ>-facts` | ステップ1-5。現状の仕様が複数モジュールに跨るとき | 仮説は渡さない | claude | `claude-opus-5-5` | medium | 10 分 |
| 盲検仮説生成 | `pi-<テーマ>-hypo` | ステップ2-1。毎回 | ホストの候補・ユーザーの本命案・確信度 | `--challenger` | `--challenger-model` | high | 10 分 |
| 既存証拠の分類 | `pi-<テーマ>-evidence-<k>` | ステップ4-2(a)。チケット・メモが数十件を超えるとき。1 束 50 件以下 | 仮説ボード・確信度（分類基準だけ渡す） | claude | `claude-opus-5-5` | low | 10 分／束 |
| 市場・競合調査 | `pi-<テーマ>-market` | ステップ4-2(a)。「競合がやっている」「市場がある」を検証するとき | ホストの見立て | claude | `claude-opus-5-5` | medium | 15 分 |
| プレモーテム | `pi-<テーマ>-premortem` | ステップ5-4。一方通行の判断では必須 | ホストが推す理由・ボード・棄却案 | `--challenger` | `--challenger-model` | high（一方通行は xhigh） | 10 分 |
| リント | `pi-<テーマ>-lint` | ステップ6-2 | なし | claude | `claude-opus-5-5` | low | 5 分 |

- **分類を low にする理由**：分類は基準を機械的に当てはめる作業で、effort を上げると基準を再解釈し始める。基準の良し悪しはホストが抜き取り検査で見る
- **個人情報**：チケット・メモを渡す前に、氏名・連絡先・契約情報が含まれていないかを確認する。含まれていればユーザーに伏せ方を確認してから渡す
- **トークンが厳しいときの段階的な切り下げ**：分類とリントを `claude-haiku-5-5` / low に。判断を含む役割は最後まで Opus に残す
- fork（ホストの文脈を引き継ぐ Agent ツール）は使わない。盲検が崩れ、出力単価も高い

## 起動手順

```bash
THEME=csv-export                      # ステップ0 で決めたテーマ名
ROLE=evidence-1                       # facts / hypo / evidence-<k> / market / premortem / lint
NAME="pi-$THEME-$ROLE"
KIND=claude                           # hypo / premortem は --challenger の値
MODEL=claude-opus-5-5                 # hypo / premortem は --challenger-model の値
EFFORT=low                            # 役割表のとおり
AGENT_ARGS=""                         # --agent-args があればその内容。無ければ空

# 名前の衝突を避ける（生きているエージェントの中で一意）
if herdr agent list | jq -r '.result.agents[].name // empty' | grep -qx "$NAME"; then NAME="$NAME-2"; fi

OUT=$(herdr tab create --workspace "$HERDR_WORKSPACE_ID" --cwd "$PWD" --label "$NAME" --no-focus)
TAB=$(echo "$OUT"  | jq -r '.result.tab.tab_id')
PANE=$(echo "$OUT" | jq -r '.result.root_pane.pane_id')

case "$KIND" in
  claude) herdr agent start "$NAME" --kind claude --pane "$PANE" -- --model "$MODEL" --effort "$EFFORT" $AGENT_ARGS ;;
  codex)  herdr agent start "$NAME" --kind codex  --pane "$PANE" -- ${MODEL:+-m "$MODEL"} $AGENT_ARGS ;;
esac
```

- `--workspace "$HERDR_WORKSPACE_ID"` と `--no-focus` を省略しない。タブ内で分割しない
- `agent start` の応答で `.result.agent.agent_status` が `idle`、`interactive_ready: true` を確認する。`agent_not_ready` や `blocked` なら `herdr agent read "$NAME" --source visible` で画面を読み、ユーザーに見せて指示を仰ぐ
- codex の effort は CLI の既定に任せる。ユーザーが指定した場合だけ `--agent-args` で渡す
- 起動に失敗して続行できない場合は、自分が作ったタブだけ `herdr tab close "$TAB"` で閉じてから報告する
- タブ名・TAB・PANE・役割・ラウンドをログの付録「サブエージェントの記録」に残す

## 送信と回収

```bash
PROMPT=$(cat <<'__PROMPT__'
<ブリーフ固定文（共通前文 + 役割本文）>
__PROMPT__
)

# 単発
herdr agent prompt "$NAME" "$PROMPT" --wait --timeout 900000
herdr agent read "$NAME" --source recent-unwrapped --lines 300

# 並列（証拠の分類を束ごとに）: 全員に送ってから 1 つずつ待つ
herdr agent prompt "pi-$THEME-evidence-1" "$PROMPT1"
herdr agent prompt "pi-$THEME-evidence-2" "$PROMPT2"
herdr agent wait "pi-$THEME-evidence-1" --timeout 900000
herdr agent wait "pi-$THEME-evidence-2" --timeout 900000
herdr agent read "pi-$THEME-evidence-1" --source recent-unwrapped --lines 400
herdr agent read "pi-$THEME-evidence-2" --source recent-unwrapped --lines 400
```

- 応答の状態で分岐する：`done` / `idle` → 回収、`blocked` → 画面を読んでユーザーに提示、`agent_prompt_stalled` → `herdr agent get` と `agent read` で確認、`timeout` → 進捗を報告して待つか中断するかを聞く
- 分類結果は表が長くなる。`--lines` を増やしても先頭が読めないときは、フォールバックとして scratchpad に書かせる：

```bash
herdr agent prompt "$NAME" "直前の回答の全文を Markdown で <scratchpad>/pi-$THEME/$NAME.md に書き出し、そのパスだけを返答してください。" --wait --timeout 120000
```

- 証拠の束を渡すときは、本文をプロンプトに貼るのではなく **ファイルのパスを渡して読ませる**（同じ cwd で動いている）。束ごとにファイルを分けておく（`<scratchpad>/pi-<テーマ>/evidence/bundle-1.md` 等）

## ブリーフ固定文

サブエージェントは呼び出し元の会話を一切知らない。**共通前文 + 役割本文** で自己完結させる。`<...>` はホストが埋める。盲検の欄に書いたものは埋めない。

### 共通前文（全役割）

```
あなたはプロダクト探究の「<役割名>」です。このタブの外の会話は知らない前提で、以下に書かれたことだけを根拠に作業してください。

制約:
- リポジトリのファイルを変更しない。コミットしない。作業用のファイルは <scratchpad>/pi-<テーマ>/<役割>/ 配下にだけ作る
- 推測を事実のように書かない。事実には根拠（file:line、引用元のファイルと行、URL と日付、数値）を添える
- ユーザーの気持ち・ニーズ・反応を推測して書かない。資料に書かれていること（誰が、いつ、何をした・何と言った）だけを扱う
- 確信度・パーセント・「おそらく」「推奨」のような評価は書かない。観測と、指定された形式だけを返す
- 返答は最後にまとめて指定の形式で出す。長くなる表はそのまま返答に含めてよい
- 判断に迷う承認（削除・push・外部送信）は実行せず、その旨を返答に書く
```

### 事実棚卸し（`pi-<テーマ>-facts`）

```
役割: 現状の仕様の棚卸し（読み取り専用）
対象: <ディレクトリ・モジュール>
知りたいこと:
- <問い 1。「〜は今どう振る舞うか」「〜はどこで記録されているか」の形>
- <問い 2>

依頼:
- 対象のコードを読み、上の問いに事実として答えてください。改善案は不要です
- 関連するイベント・ログ・メトリクスが記録されている箇所があれば、それも事実として挙げてください（何が測れるかを知りたい）
- 事実ごとに根拠を file:line で示してください
- 読んでも分からなかったことは、分からなかったと書いてください

返答形式:
## 事実
| ID | 事実 | 根拠（file:line） |
| --- | --- | --- |
## 記録されているイベント・ログ・メトリクス
| 名前 | 何を記録しているか | 根拠（file:line） |
| --- | --- | --- |
## 確認できなかったこと
- <項目>: <なぜ確認できなかったか>
```

### 盲検仮説生成（`pi-<テーマ>-hypo`）

```
役割: 仮説の独立生成
中核の問い: <1-1>
ユーザーの成果条件:
- <1-2>
事業の成果条件と制約:
- <1-2>
現状の事実:
- <1-5 の一覧。F-ID と根拠付き>
手元にある証拠の在庫（種類と量だけ）:
- <例: サポートチケット 412 件（過去 90 日）、インタビューメモ 3 本、利用ログあり（イベント X, Y）>

依頼:
- この問いに対する候補を、次の 3 種類に分けて挙げてください
  - 課題仮説（誰が、どの状況で、何に困り、今どう対処しているか）を 3〜5 個。「課題は無い、または十分に小さい」を必ず 1 つ含めてください
  - 解決仮説（どの手段がその課題を軽減するか）を 3〜5 個。「作らない」「運用・ドキュメント・既存機能の改善で足りる」「ソフトウェアでない解決」を必ず含めてください
  - 価値仮説（その手段のためにユーザーは行動を変えるか、払うか、使い続けるか）を各解決仮説に 1 つ。「言うが行動は変えない」を必ず含めてください
- 各仮説について「正しければ、手元の証拠や 5 人程度のインタビューで何が観測されるはずか」「間違っていれば何が観測されるはずか」を、指標・閾値・条件の形で書いてください
- 必要なら <ディレクトリ> のコードや <証拠ファイルのパス> を読んで構いません。読んだ場合は根拠を示してください
- 候補の優劣・おすすめ・確信度は書かないでください

返答形式:
## 課題仮説
### 課題 1: <名前>
- 内容（誰が / どの状況で / 何に困り / 今どう対処しているか）:
- 正しければ観測されるはずのこと:
- 間違っていれば観測されるはずのこと:
## 解決仮説
### 解決 1: <名前>（対応する課題: 課題 <n>）
- 内容:
- 正しければ観測されるはずのこと:
- 間違っていれば観測されるはずのこと:
## 価値仮説
### 価値 1: <名前>（対応する解決: 解決 <n>）
- 内容:
- 正しければ観測されるはずのこと:
- 間違っていれば観測されるはずのこと:
```

### 既存証拠の分類（`pi-<テーマ>-evidence-<k>`）

```
役割: 既存証拠の分類（基準の機械的な適用）
対象ファイル: <scratchpad>/pi-<テーマ>/evidence/bundle-<k>.md （<N> 件。各件に ID が付いている）

分類基準:
| 分類 | 定義 | 該当する例 | 該当しない例 |
| --- | --- | --- | --- |
| A | <仮説の予測から作った定義> | <例> | <例> |
| B | <定義> | <例> | <例> |
| 該当なし | 上のどれにも当てはまらない | | |
| 判定不能 | 情報が足りず判定できない | | |

依頼:
- 各件を上の基準で 1 つの分類に振り分けてください。複数に当てはまる場合は最も強く当てはまる 1 つを選び、備考に他の候補を書いてください
- 各件について、その件が「ユーザーが実際にやったこと（行動）」を含むか、「言っていること（発言・要望）」だけかを記録してください
- 分類の根拠として、該当箇所を 1 文だけ引用してください。要約や言い換えをしないでください
- 基準に無い新しい分類を作らないでください。当てはまらなければ「該当なし」、迷えば「判定不能」にしてください
- 件数の傾向・意味・示唆は書かないでください

返答形式:
## 分類結果
| ID | 分類 | 行動 / 発言 | 根拠の引用 | 備考 |
| --- | --- | --- | --- | --- |
## 集計
| 分類 | 件数 | うち行動を含む件数 |
| --- | --- | --- |
## 基準の適用で迷った点
- <どの件で、どの分類とどの分類で迷ったか。基準のどこが曖昧か>
```

### 市場・競合調査（`pi-<テーマ>-market`）

```
役割: 市場・競合の事実調査
調べたいこと:
- <例: 競合 X, Y, Z に「<機能>」に相当するものがあるか。あるなら提供形態（標準 / 上位プラン / 有償オプション）と価格>
- <例: その機能について第三者（レビューサイト・事例・コミュニティ）が言及している件数と内容>
- <例: 公開されている利用率・採用事例の数値>

依頼:
- 公開情報を調べ、事実だけを出典 URL と確認日付付きで列挙してください
- ベンダー自身の主張（公式サイト・プレスリリース）と第三者の情報（レビュー・事例・記事）を分けて記録してください
- 見つからなかったことも「見つからなかった」と書いてください。見つからないこと自体が観測です
- 「だから我々も作るべき」「市場性がある」のような結論・示唆は書かないでください

返答形式:
## 事実
| # | 事実 | 種別（ベンダー主張 / 第三者） | 出典 URL | 確認日 |
| --- | --- | --- | --- | --- |
## 見つからなかったこと
- <調べたが見つからなかった項目と、どこを探したか>
```

### プレモーテム（`pi-<テーマ>-premortem`）

```
役割: プレモーテム（事前検死）
前提: 次の案を採用してリリースし、6 か月後に「失敗だった」と判断されたとします。
採用案:
<案の内容。誰に何を提供するか。ホストが推す理由・比較表・棄却案は含めない>
ユーザーの成果条件・事業の成果条件・制約:
- <1-2>
現状の事実:
- <1-5>

依頼:
- 失敗の最もありそうな理由を 3 つ、ありそうな順に挙げてください。「使われない」「使われたが価値につながらない」「別の人や機能に悪影響が出た」「運用・サポートが回らない」「価格・契約で揉めた」のような種類の違う理由を含めてください
- 各理由について、リリース前の今の時点でそれを観測・検証できる方法を 1 つ、指標・閾値・条件・サンプル数の形で書いてください
- 案の良い点、採用の是非、代替案は書かないでください

返答形式:
## 失敗理由
### 1. <理由>
- なぜ起きるか:
- 今観測できる形（指標・閾値・条件・サンプル数）:
### 2. <理由>
...
### 3. <理由>
...
```

### リント（`pi-<テーマ>-lint`）

```
役割: 探究ログのリント（形式チェックのみ）
対象: <ログのパス>（読み取り専用。変更しない）

チェック項目:
1. 「3. 反証条件の事前登録」の登録日時が「4. 探究ループ」の最初のラウンドの日時より前か
2. 「確信度の更新」のすべての行に、根拠となる観測 ID（O-番号）が付いているか
3. すべての観測に「証拠の種類」（行動 / 実験 / 発言 / 社内意見）と「サンプル数」が付いているか
4. すべての kill 条件に指標・閾値・条件・サンプル数の 4 要素があるか
5. 仮説ボードに「課題は無い／小さい」「作らない」「行動は変えない」のいずれかの帰無仮説が含まれているか
6. ユーザーに関する主張で、出典が無いのに ⚠️ も付いていないものが無いか
7. 「6. 判断記録」の「覆す条件」が、観測可能な形で書かれているか
8. 「5-3 可逆性と閾値」で一方通行と分類された候補に、「5-4 プレモーテム」の結果が付いているか
9. 仮説ボードの各仮説に「種別」と「出自」が書かれているか
10. 状態が「検証待ち」なら、「4. 検証計画」に 実行者・期限・持ち帰るもの が揃っているか

内容の良し悪し（仮説の妥当性、決定の是非）は判定しないでください。

返答形式:
| # | 項目 | 結果（✅ / ❌） | 該当箇所（❌ のとき） |
| --- | --- | --- | --- |
```

## ホスト側の受け取り規則

- 返答から **観測だけ** を取り出し、O-ID と証拠の種類とサンプル数を付けてログに転記する。サブエージェントが解釈・推奨を書いてきても採用しない
- **分類結果は抜き取り検査する。** 10 件をホストが基準どおりに再分類し、2 件以上ずれたら基準を直して束を再分類させる。検査結果（何件中何件一致）をログに書く
- **決定を変えうる観測は、ホストが元データ（チケット原文・集計のクエリ・出典 URL）を確認する。** 確認できなければ ⚠️
- 市場調査の「ベンダー主張」は発言と同じ強さ、「第三者」でも採用事例の数値は行動に近い強さとして扱う
- 「基準の適用で迷った点」は分類基準の欠陥か、仮説の予測が曖昧である兆候。ボードに戻って kill 条件の指標を見直す
- 盲検仮説生成の候補にホストの候補と同じものがあっても、出自は両方を記録する（独立に同じ候補が出たこと自体が情報）
- 対抗役がユーザーの本命案を言い当てても、それは独立の収束であって漏洩ではない。ブリーフに本命を書いてしまっていた場合だけ、盲検が崩れたとしてログに記す

## タブの後始末

- 既定ではタブを閉じない。再開時に同じ束の再分類や追加調査を同じタブに頼める
- `--close` またはユーザーの指示があったときだけ、このスキルが作ったタブを `herdr tab close "$TAB"` で閉じる。他のタブ・ペイン・ワークスペースに触らない
- サブエージェントがリポジトリ内のファイルを変更していた場合は `git status --short` で確認し、ユーザーに報告する
