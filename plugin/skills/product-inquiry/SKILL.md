# プロダクト探究スキル（product-inquiry）

「何を作るべきか」が決まらない状態（本当に課題なのか分からない、どの方向で解くべきか分からない、どこまで作るか決められない）を、**課題・解決・価値の仮説を立て、反証条件を先に書き、最も安い証拠から壊しに行き、確信度を更新して、可逆性に見合う確信度で決める** ループで解消します。成果物は探究ログ 1 本で、その中心は仮説ボードです。

technical-inquiry と同じ骨格ですが、決定的に違う前提が 1 つあります。**プロダクトの証拠（ユーザーの行動・発言）は、エージェントが自分では取りに行けない。** だからこのスキルは、エージェントが集められる証拠（既存のチケット・ログ・インタビューメモ・利用データ・競合情報・現状の仕様）を先に使い切り、それで潰せない仮説だけを **人が実行する検証計画** にしてユーザーに渡し、結果を持ち帰ってもらって再開します。探究は複数セッションにまたがるのが普通です。

このスキルが守る 3 つの規律：

1. **反証条件を、調べる前に書く。** 「ユーザーに聞いてみる」の前に、「何人がどう答えたら棄却か」を決める。
2. **確信度で持ち、証拠の強さで重みを変える。** 行動 ＞ 実験 ＞ 発言 ＞ 社内の意見。少ないサンプルで大きく動かさない。
3. **可逆性で決める。** 限定ベータやフラグで戻せる判断は低い確信度で進めてよく、価格・公開 API・機能削除のような戻せない判断は高い確信度を要求するか、先に戻せる形にする。

役割分担：**ホスト**が仮説ボードを所有し、問いの設定・確信度の更新・統合・ユーザーとの対話を行う。**サブエージェント**（Herdr の別タブ）は対立仮説の生成・既存証拠の分類・市場調査・プレモーテムを担い、観測だけを返す。**検証はユーザーとチームが実行し、決めるのは PO（ユーザー）。**

## 入力

```
# Claude Code（ybaba プラグイン経由）
/ybaba:product-inquiry <課題感・要望・資料> [--out <探究ログの保存先>] [--mode discover|solve|scope]
                       [--challenger claude|codex] [--challenger-model <モデル>] [--rounds N]
                       [--agent-args "<引数>"] [--no-subagents] [--close]

# 再開（検証結果の持ち帰り）
/ybaba:product-inquiry --out <既存の探究ログ> <検証結果の本文またはファイル>

# OpenAI Codex CLI
$ybaba:product-inquiry <課題感・要望・資料> [...]    # marketplace 経由のプラグイン
$product-inquiry <課題感・要望・資料> [...]          # ~/.agents/skills/ fallback 導入時
```

| オプション | 既定値 | 意味 |
| --- | --- | --- |
| `<課題感・要望・資料>` | 必須 | ざっくりした要望、PBI のタイトル、ユーザーの声、サポートチケットのエクスポート、インタビューメモ、利用データ、競合情報。複数可。ディレクトリも可 |
| `--out` | なし | 探究ログの保存先。**未指定なら開始前に質問する**。既存のログを指定すると再開になる |
| `--mode` | 自動判定 | `discover`＝課題探索、`solve`＝解決策選定、`scope`＝仕様の線引き。判定結果は着手前に確認する |
| `--challenger` | `claude` | 対抗役（仮説生成・プレモーテム）のエージェント種別。`codex` にすると系統を変えて盲点の相関を減らせる |
| `--challenger-model` | claude なら `claude-opus-5-5`、codex なら codex の既定 | 対抗役のモデル |
| `--rounds` | 3 | 探究ループの最大ラウンド数。人が実行する検証をまたぐラウンドも 1 と数える |
| `--agent-args` | なし | サブエージェント起動時の追加引数。**ユーザーが明示したときだけ**付ける |
| `--no-subagents` | なし | ホスト単独で回す。Herdr 外や軽い探究向け。独立性が落ちることをログに明記する |
| `--close` | 付けない | 終了時にこのスキルが作ったタブを閉じる。既定は残す |

## 3 つのモード

| モード | 問いの形 | 中心になる仮説 | kill 条件の典型 | 決定の形 |
| --- | --- | --- | --- | --- |
| **課題探索** `discover` | 「誰の、どの課題が、どれほど痛く、今どう対処されているか」 | 課題仮説：「セグメント S は状況 C で課題 P を持ち、代償 L を払っている」 | 「S の 5 人に過去の行動を聞き、3 人未満しか自力で対処した経験が無ければ棄却」 | 取り組む課題と対象セグメント、または「課題は小さい」の確認 |
| **解決策選定** `solve` | 「その課題を、どの方向の解決策で解くべきか」 | 解決仮説：「手段 M は S の課題 P を軽減する」、価値仮説：「S は M のために行動を変える／払う」 | 「プロトタイプで主要タスクを 5 人に試させ、介助なしで完了が 3 人未満なら棄却」 | 解決の方向と、棄却した方向の理由 |
| **仕様の線引き** `scope` | 「その方向で、最初に何を入れ、何を外すか」 | 価値仮説の分解：「要素 E が価値の大半を生む」「要素 F が無くても S は使う」 | 「F 無しのベータで 14 日後の週次利用が 5 社未満なら F を入れる」 | やる・やらないの一覧と理由、リリース後の成功指標と停止条件 |

モードは入力から推定し、保存先の質問と一緒にユーザーに確認する。課題が未確認のまま解決策や仕様の話が来たときは、**課題探索を先に短く回す**ことを提案する（課題仮説が崩れると解決仮説も価値仮説も全部崩れる）。

## 全体の流れ

1. **問いを立てる** — 中核の問い、成果条件と事業制約、前提の棚卸し、分解、現状の事実と証拠の在庫
2. **仮説を立てる** — 対抗役に盲検で候補を出させ、ホストの候補と統合し、課題→解決→価値の連鎖と最もリスクの高い仮説を特定し、初期確信度を付ける
3. **反証条件を先に書く** — 仮説ごとに kill 条件（指標・閾値・条件・サンプル数）と検証手段、実行者を事前登録する。**ここまで仮説を試す調査禁止**
4. **調べて更新する** — エージェント内で完結する検証（既存証拠の分類・市場調査・コード事実）を先に回し、残った仮説を人が実行する検証計画にして渡す。結果が戻ったら一括で確信度を更新する
5. **統合して決める** — ステークホルダーの対立と統合、波及、可逆性と閾値、プレモーテム、比較。推奨を添えて PO が決める
6. **記録して渡す** — 判断記録、リント、create-pbi / design-doc への素案、リリース後の指標、TL;DR

ユーザーに確認を取るのは原則 3 回：ステップ1 の終わり（問い・成果条件・前提）、ステップ3 の終わり（ボードと反証条件）、ステップ5（決定）。検証計画を渡すときはセッションが一度終わる。

## ステップ0: 前提と入力を確認する

```bash
test "${HERDR_ENV:-}" = 1 && echo "in herdr: workspace=$HERDR_WORKSPACE_ID"
herdr agent start --help | grep -q -- '--kind' && echo "herdr 0.8+"
```

- 入力をすべて読む。ディレクトリなら配下を一通り読む。**ユーザーの生の言葉**（要望の原文、PBI の背景、ユーザーの声の引用）を見つけて引用できるようにしておく
- 入力に「こう作りたい」という解決策が含まれていたら、それは **ユーザーの本命案** として記録し、ステップ2 の対抗役には見せない
- モードを推定する
- 保存先を `--out` または本文から読み取る。読み取れなければ質問する
- `HERDR_ENV` が `1` でなければ、`--no-subagents`（ホスト単独）で続けるか中断するかを聞く
- 以上の質問は **1 回にまとめて聞く**
- 探究のテーマ名を英小文字ケバブケースで短く決める（例: `csv-export`、`onboarding`）。サブエージェントのタブ名 `pi-<テーマ>-<役割>` に使う。32 文字以内に収める
- `assets/inquiry-log-template.md` を Read し、その形式で保存先に探究ログを作る。以後、各ステップとラウンドの終わりにログを保存する

### 再開

指定された保存先に既にログがある場合は **再開** として扱う：

1. ログを読み、仮説ボード・事前登録済みの反証条件・検証計画・付録のサブエージェント記録を引き継ぐ
2. ログの状態が「検証待ち」で、入力に検証結果が含まれていれば、ステップ4-3（回収）から続ける。結果が一部の仮説だけなら、揃った仮説だけ更新し、残りは検証待ちのまま残す
3. 入力に検証結果が無ければ、どこで止まっていたかを 1 行で伝え、続きから進める

別の探究を同じパスに書こうとしている場合だけ、上書きの確認をする。

## ステップ1: 問いを立てる

`assets/question-bank.md` を Read し、「成果条件を見つける問い」「前提を崩す問い」の節を使う。ここはユーザーとの対話が中心で、サブエージェントに任せない。

### 1-1 中核の問い

What の形で 1 文にする。「誰の、どの課題を、どこまで解くべきか」。ユーザーの生の言葉を引用する。機能名（「CSV エクスポート」）ではなく、ユーザーの状況と成果（「月次で一覧を外部に渡す作業」）で書く。

### 1-2 成果条件と事業制約

「機能」から「成果」まで戻す。

- **ユーザーの成果条件**：対象ユーザーがこの件で達成したいこと。「〜できる」ではなく「〜という状態になる」。測り方を添える
- **事業の成果条件**：この件で事業が得たいこと（売上、解約抑止、工数削減、契約条件の充足）。測り方を添える
- **事業制約**：法規制、契約、ブランド、予算、期日など、破れない条件。出典を付ける
- 出典の無い「条件」は制約ではなく前提候補として 1-3 へ回す

### 1-3 前提の棚卸し

「ユーザーは〜を求めている」「営業が〜と言っている」「競合がやっている」「経営の指示」「昔からの要望」を列挙し、1 つずつ問う：**誰の前提か／根拠は行動か発言か意見か／いつのものか、今も成り立つか／外したら何が起きるか／それは制約か好みか**。

- 根拠が社内の意見だけの前提は、不変の前提ではなく **検証対象の仮説** としてステップ2 に回す
- 確認できた制約は 1-2 に昇格させる
- 判断が PO に要るものは「要確認」として確認事項に載せる

### 1-4 分解

中核の問いを **課題 → 解決 → 価値** の連鎖と、対象セグメントの軸で分ける。

- 課題：誰が、どの状況で、何に困り、今どう対処しているか
- 解決：どの手段がその課題を軽減するか（作らない・運用で解く・既存機能の改善を含む）
- 価値：その手段のためにユーザーは行動を変えるか、払うか、使い続けるか
- セグメント：課題の痛さが違う集団があるなら分ける。全員向けの平均で考えない

### 1-5 現状の事実と証拠の在庫

事実には根拠を付け、ID（F1, F2, …）を振る。

- **現状の仕様**：プロダクトが今どう振る舞うか。コードを読んで確認する。対象が広ければ `assets/subagent-briefs.md` の「事実棚卸し」ブリーフで `pi-<テーマ>-facts` タブに任せる（読み取り専用）
- **何が測れるか**：関連するイベント・ログ・メトリクスが既に取られているか。取られていなければ、取り始めること自体が最初の検証手段になる
- **証拠の在庫**：手元にある証拠を種類・量・期間で棚卸しする（サポートチケット N 件／期間、インタビューメモ N 本、利用ログの有無、営業からの声、競合の公開情報）。これがステップ4 で「エージェントが先に潰せる仮説」の範囲を決める
- ユーザーに関する主張で出典が無いものは、ここに事実として書かない。⚠️ を付けて前提候補（1-3）に回す

### 確認

1-1〜1-5 をログの「1. 問い」に書き、ユーザーに確認する。成果条件と前提の仕分けは PO の判断が要ることが多い。

## ステップ2: 仮説を立てる

### 2-1 対抗役に盲検で候補を出させる（先に出す）

`pi-<テーマ>-hypo` タブに `--challenger` のエージェントを立て、`assets/subagent-briefs.md` の「盲検仮説生成」ブリーフを送る。**渡すのは中核の問い・成果条件・事業制約・現状の事実・証拠の在庫の要約だけ。** ホストの候補、ユーザーの本命案、確信度は含めない。

### 2-2 ホストも並行して候補を書く

対抗役を待つ間に、ホストも候補を手元に書く。

### 2-3 統合する

- 重複をまとめ、各仮説に **種別**（課題／解決／価値）と **出自**（ユーザー／ホスト／対抗役）を記録する
- 必ず含めるもの：
    - **「課題は無い、または十分に小さい」**（課題の帰無仮説）
    - **「作らない」「運用・ドキュメント・既存機能の改善で足りる」**（解決の現状維持案）
    - **「言っているが行動は変えない」**（価値の帰無仮説）
- 全候補が同じ方向を向いていたら、対抗役に「これら以外で、前提の 1 つを外した候補を」と追加依頼する
- 課題→解決→価値の **連鎖** を書き、**崩れたら方向ごと倒れる仮説**（最もリスクの高い仮説）に ★ を付ける。★ が最初の検証対象になる

### 2-4 初期確信度を付ける

- 10% 刻みの粗い数値。精度を主張しない
- 根拠欄に **証拠の種類** を必ず書く：行動／実験／発言／社内意見／事前の見立て。観測が無ければ「未評価」
- 課題仮説とその帰無仮説、価値仮説とその帰無仮説は競合するので、合計がおおむね 100% になるように付ける

仮説ボードをログの「2.」に書く。ユーザー確認はステップ3 とまとめて行う。

## ステップ3: 反証条件を先に書く

`assets/question-bank.md` の「kill 条件の書き方」「検証手段と証拠の強さ」「インタビューで聞く問い・聞かない問い」を使う。仮説ごとに次を書く。

| 項目 | 要件 |
| --- | --- |
| **kill 条件** | 「これが観測されたら棄却」を **指標・閾値・条件・サンプル数** で書く。「反応が良ければ」は不可。例:「対象セグメント 5 人に過去 1 か月の行動を聞き、自力で対処した経験があるのが 3 人未満なら棄却」 |
| **検証手段** | 最も安く、最も強い証拠が得られる手段。順序は 既存データ・チケットの分類 → 利用ログの集計 → 少人数インタビュー → フェイクドア・コンシェルジュ → プロトタイプテスト → 限定ベータ |
| **証拠の種類** | その手段で得られるのは行動か実験か発言か。発言しか得られない手段は、過去の行動を聞く設計にする |
| **実行者** | ホスト／サブエージェント（既存証拠がある場合）／ユーザー・チーム（人に当たる場合） |
| **情報価値チェック** | 「結果がどちらに転んでも判断は同じか」。同じならやらない |
| **想定コスト・期限** | 人が実行する検証は、誰が・いつまでに・何人に |
| **優先度** | ★ の仮説を壊す検証が最優先。次に情報価値 ÷ コスト |

- 「使いますか？」「いくらなら払いますか？」のような **未来の意向を聞く検証を kill 条件の根拠にしない**。過去の行動か、実際にやらせる実験に言い換える
- ログの「3. 反証条件の事前登録」に **登録日時** を入れる。以後 kill 条件を変える場合は変更履歴に理由付きで残す。結果を見てから緩めない

### 確認

ボードと反証条件をまとめてユーザーに見せ、仮説の過不足・kill 条件の妥当性・人が実行する検証の現実性（誰に当たれるか、何人集まるか）を確認する。

## ステップ4: 調べて更新する（探究ループ）

1 ラウンド＝「検証を選ぶ → 実行する → 回収する → 一括で更新する → 停止判定」。最大 `--rounds` 回。**エージェント内で完結する検証を先に回し、それで潰せない仮説だけを人に渡す。** 人の時間が一番高い。

### 4-1 検証を選ぶ

優先度順に、このラウンドで回す検証を選ぶ。★ を後回しにしない。

### 4-2 実行する

**(a) エージェント内で完結する検証**

| 種類 | やり方 | タブ |
| --- | --- | --- |
| 既存証拠の分類 | チケット・インタビューメモ・問い合わせを、仮説の予測から作った **分類基準** で分類する。1 束 50 件以下に分け、束ごとに並列。基準には「該当なし」「判定不能」を必ず含める。ホストが 10 件を抜き取って再分類し、2 件以上ずれたら基準を直してやり直す | `pi-<テーマ>-evidence-<k>` |
| 利用ログ・メトリクスの集計 | 何が測れるか（1-5）に基づき集計する。数コマンドならホストが自分でやる | ホスト |
| 市場・競合調査 | 競合の該当機能、第三者のレビュー・事例、公開されている価格・採用状況。出典 URL と日付付きで事実だけ | `pi-<テーマ>-market` |
| 現状の仕様の確認 | 「今でもできる」「回避策がある」の確認 | ホスト or `pi-<テーマ>-facts` |

ブリーフは `assets/subagent-briefs.md` の固定文を使う。送信は `--wait` 無しで全員に送り、1 つずつ `herdr agent wait` する。`blocked` は画面を読んでユーザーに提示する。

**(b) 人が実行する検証**

(a) で潰れなかった仮説について、ログの「4. ラウンド N / 検証計画」に次を書き、ログの状態を **「検証待ち」** にして保存し、セッションを終える：

- **検証計画表**：仮説／kill 条件／手段／対象と人数／誰が／期限／持ち帰るもの
- **インタビューガイド**（インタビューがある場合）：仮説ごとに、過去の行動を聞く問いを 5〜8 個。誘導する問い・未来の意向を聞く問いが混ざっていないか `assets/question-bank.md` で点検する
- **実験の設計**（フェイクドア・プロトタイプ・ベータがある場合）：何を見せ、何を測り、いくつで判定するか
- **結果の持ち帰りフォーマット**（下記）

ユーザーには「結果が揃ったら、同じ保存先を指定してこのスキルを呼び直してください。一部だけでも構いません」と伝える。

```
## 検証結果: H<N>
- 実施: <手段・対象・人数・日付>
- 観測: <事実。発言は引用、行動と数値はそのまま。解釈を混ぜない>
- kill 条件に該当: はい / いいえ / 判定不能（理由）
- 想定外: <あれば>
```

### 4-3 回収する

(a) のタブの返答と (b) の持ち帰り結果から **観測だけ** を取り出し、ID（O1, O2, …）と **証拠の種類**（行動／実験／発言／社内意見）と **サンプル数** を付けてログに転記する。

- サブエージェントが解釈・推奨を書いてきても採用しない
- 持ち帰り結果に解釈が混ざっていたら、観測と解釈を分けて転記する（解釈は捨てずに「ユーザーの解釈」として残す）
- 決定を変えうる観測は、ホストが元データ（チケット原文・集計のクエリ）を確認する。確認できなければ ⚠️
- 「想定外」は新仮説の候補。テストする前にステップ2〜3 を通す

### 4-4 一括で更新する

全観測が揃ってから、仮説ごとに「前 → 後」と「根拠となる観測 ID」を書く。

- **証拠の強さで動かし方を変える**：行動データと実験は大きく、過去の行動についての発言は中程度、未来の意向と社内意見はほとんど動かさない
- **サンプル数を根拠に書く**：5 人のインタビューで 20% → 70% のような動かし方をしない。小さいサンプルは「方向」を示すだけで「大きさ」は示さない
- 観測の無い仮説は動かさない。kill 条件に該当した仮説は「棄却」にする
- 帰無仮説（課題は無い／行動は変えない）の確信度も同時に更新する

### 4-5 停止判定

| 条件 | 次 |
| --- | --- |
| ★ を含む主要な仮説の kill 条件をすべて評価した | ステップ5 へ |
| 残る不確実性が決定を変えない | ステップ5 へ |
| `--rounds` に達した | ユーザーに 3 択：今の確信度で決める／可逆化（限定ベータ・フラグ）して決める／待つ（待つコスト＝その間に作れないもの・逃す機会を明記） |

ラウンドの終わりに、変わった仮説だけを短く報告して次へ進む。

## ステップ5: 統合して決める

`assets/question-bank.md` の「波及の問い」「可逆性の問い」「統合の問い」「プレモーテムの問い」を使う。

### 5-1 ステークホルダーの対立と統合

営業・サポート・運用・経営・ユーザーセグメント間で望むことが違うなら、対立表を書く：誰が／何を望むか／何を守りたいか／根拠は証拠か意見か／対立の根にある前提。両者が守ろうとしているものが実は同じなら統合案が出る。統合案は新しい仮説としてボードに足し、kill 条件を付けてから採用候補にする。**折衷（全員の要望を少しずつ入れる）は統合ではない。**

### 5-2 波及

採用候補ごとに：得する人と損する人、他のセグメント・他の機能への影響、サポート・運用の負荷、価格・プランとの整合、インセンティブの歪み（この機能のせいでユーザーが望ましくない行動を取らないか）、使わない人の体験は変わらないか。

### 5-3 可逆性と閾値

| 可逆性 | プロダクトでの例 | 決定に必要な確信度の目安 |
| --- | --- | --- |
| **二方向** | フラグで出し分け、限定ベータ、社内先行、運用・ドキュメントで解く、静かに引っ込められる機能 | 60% 以上 |
| **一方通行** | 価格変更、公開 API・連携、契約・SLA の約束、ユーザーに見えるデータ構造、機能の削除、訴求・ブランドの変更 | 90% 以上、**または先に二方向にする** |

一方通行の候補には、可逆化の手段（限定公開、期間限定、オプトイン、新旧併存）を先に検討する。閾値は目安で、PO と合意して変えてよい。変えた場合は理由をログに書く。

### 5-4 プレモーテム

`pi-<テーマ>-premortem` タブに対抗役を立て、`assets/subagent-briefs.md` の「プレモーテム」ブリーフを送る。渡すのは **採用候補の内容・成果条件・事業制約・現状の事実だけ**。

返ってきた失敗理由を仕分ける：**評価済み**（観測 ID を添える）／**未評価**（新しい kill 条件候補。もう一周回すか、残リスクとして記録するかを PO に聞く。一方通行なら未評価を残したまま決めない）／**不採用**（理由）。二方向の判断では省略してよい。省略した場合はその旨を書く。

### 5-5 比較と推奨

| 候補 | 期待価値（誰に・何が・どれだけ） | 成功確率（確信度） | コスト | 失敗時損失 | 可逆性 | 待つコスト | 備考 |

推奨を 1 つ、理由付きで書く。**決定は PO。** 決定・保留・差し戻し（もう一周）のどれかを受け取る。`scope` モードでは、決定は「やる・やらないの一覧」と「リリース後の成功指標・停止条件」のセットになる。

## ステップ6: 記録して渡す

### 6-1 判断記録

ログの「6. 判断記録」に書く：決定／根拠（観測 ID）／棄却した案と理由／**覆す条件**（何が観測されたら見直すか）／未解決・残リスク／次の一手。

### 6-2 リント

`pi-<テーマ>-lint` タブに `assets/subagent-briefs.md` の「リント」ブリーフを送る（Opus 5.5 / effort low。`--no-subagents` ならホストが同じ項目を自分で点検する）。❌ が返った項目はログを直してから次へ進む。

### 6-3 引き渡し

ログの「7. 引き渡し」に書く：

- **create-pbi 用の素案**：User Story（〜として、〜したい。なぜなら〜）、Acceptance Criteria（kill 条件を成功条件に裏返したもの）、Scope（やる・やらないと、その理由＝棄却した仮説）
- **design-doc 用の素案**：Scope／Background（現状の事実 F-ID）／ProblemStatement（課題仮説と根拠 O-ID）
- **リリース後の指標**：成功指標と停止条件。探究の kill 条件はリリース後も生き続ける
- **technical-inquiry への申し送り**：実現可能性・方式が未確認のまま残っている点

続けて使えるスキルを案内する：`create-pbi`、`design-doc`、`technical-inquiry`（どう作るか）、`extract-issues`（残った PO 決定の論点を整理する）、`issue-tree`（論点の可視化）。

### 6-4 保存と報告

保存先にログを書き出し、パスを 1 行で示したうえで全文をコンソールに出力する。返答は必ず **TL;DR** で締める。検証待ちで終えるときも同じ形で締め、「決定」の代わりに「次に検証すること」を書く。

```
## TL;DR

- 問い: <中核の問いを 1 行>
- 決定: <採用案>（確信度 <N>%、可逆性: 二方向／一方通行）  ※検証待ちなら「次に検証: <仮説と手段>」
- 決め手になった観測: <観測 ID と要点。証拠の種類とサンプル数>
- 棄却した案: <案と理由を 1 行ずつ>
- 覆す条件: <1 行>
- 確認したいこと: <PO の判断待ちがあれば。無ければ省略>
```

タブは閉じない。`--close` またはユーザーの指示があったときだけ、このスキルが作ったタブを閉じる。

## 行動規則

哲学や方法論の名前は出力に書かない。出力は「成果条件・前提・仮説・反証条件・観測・証拠の種類・確信度・可逆性・判断」の実務語彙で書く。

- **ユーザーについての主張には出典を付ける。** 出典が無ければ ⚠️ を付け、事実ではなく前提候補か仮説として扱う。**ユーザーの証拠を作らない**
- **発言と行動を分ける。** 未来の意向（「使いますか」）を kill 条件の根拠にしない。過去の行動を聞くか、実際にやらせる
- **「課題は無い」「作らない」「行動は変えない」を必ず仮説に含める**
- **反証条件を書く前に、仮説を試す調査を始めない。** 事実確認と証拠の在庫の棚卸しだけが例外
- **対抗役にホストの仮説・ユーザーの本命案・確信度を見せない**
- **確信度を 0/1 で書かない。「未評価」を許す。** 根拠に証拠の種類とサンプル数を書き、小さいサンプルで大きく動かさない
- **更新には観測 ID を添える。** 一括で更新する
- **人の時間を最後に使う。** 既存の証拠で潰せる仮説を先に潰してから検証計画を渡す
- **統合を折衷にしない。** 対立の根にある前提を問う
- **一方通行の判断にはプレモーテムを必須にする**
- **サブエージェントは観測を返す。** 解釈・推奨を書かせない。分類は基準に従わせ、ホストが抜き取りで検査する
- **ホストがボードを持つ。** サブエージェントにログを編集させない。リポジトリも変更させない
- **決めるのは PO。** 推奨は添えてよい。実現可能性の疑問は technical-inquiry に送り、ここで混ぜない

## 注意点

- **Herdr の外から操作しない**：`HERDR_ENV=1` を確認する。外なら `--no-subagents` で回すか中断する
- **タブは `tab create --workspace "$HERDR_WORKSPACE_ID" --no-focus`、1 タブ 1 エージェント、ID は JSON 応答から取る**（herdr-subagent スキルの規則をそのまま守る）
- **ダイアログに勝手に答えない**：`blocked` は画面を読んでユーザーに提示する
- **個人情報に注意**：チケットやインタビューメモをサブエージェントに渡すとき、氏名・連絡先・契約情報が含まれていないかを確認し、含まれていればユーザーに伏せ方を確認する。ログにも書かない
- **`--agent-args` は言われたときだけ**
- **閉じてよいのはこのスキルが作ったタブだけ**
- **巨大な探究は分割する**：セグメントが 3 つを超える、仮説が 8 個を超えるなら、分解（1-4）に戻って探究を分ける
- **再開に備える**：ログは常に最新の状態で保存しておく。検証待ちで終えるときは、状態・検証計画・持ち帰りフォーマットが揃っていることを確認する
