# イシューツリースキル（issue-tree）

論点を**イシューツリー**（中核の問いを頂点に、問いの分解として論点を配置したロジックツリー）に編成し、**インタラクティブな自己完結HTML** 1ファイルとして出力します。

- 左ペイン: 展開・折りたたみできるツリー。ノードには型バッジとステータス、子孫ノード数が表示される。ツールバーにインクリメンタル検索あり。21ノード以上のツリーは初期表示が2階層に畳まれる
- 右ペイン: ノードをクリックすると詳細（問い・決定・なぜ論点か・選択肢・判断材料・決定者・依存関係）を表示。依存関係はクリックで該当ノードへジャンプできる。左右の境界はドラッグで動かせる
- 外部CDN・ライブラリ依存なし。ブラウザで開くだけで動く。任意の深さのツリーに対応する

同プラグインの `extract-issues`（論点の抽出・構造化、コンソール出力）の**可視化版**という位置づけです。論点抽出の手順そのものは extract-issues のものを使います。

用途は2つあり、どちらも正規の使い方：

- **意思決定マップ**: 未決の論点を型（事実確認／Dev方針／PO決定など）で整理し、決定を消化していく地図。浅く（2〜4階層）意思決定の骨格に絞る
- **調査・計画の構造化**: 調査結果や実装計画（plan.md）を網羅的にツリーで俯瞰する。深く（5階層以上）なってよい。型は素材に合わせてカスタム定義する（後述の `types`）

## 入力

```
# Claude Code（ybaba プラグイン経由）
/ybaba:issue-tree <素材（ファイル・ディレクトリ・本文貼り付け）> [--out <出力先.html>]

# OpenAI Codex CLI
$ybaba:issue-tree <素材>    # marketplace 経由のプラグイン
$issue-tree <素材>          # ~/.agents/skills/ fallback 導入時
```

素材は次のどちらでもよい：

- **抽出済みの論点一覧**（extract-issues の出力・issues.md・会話中の論点整理）→ ステップ2から始める
- **生素材**（PBI・調査ドラフト・design-doc・会議メモ等）→ ステップ1から始める

## 全体の流れ

1. （生素材の場合）論点を抽出する — `../extract-issues/SKILL.md` の手順に従う
2. 論点をツリー構造に編成する
3. データJSONを作る
4. テンプレートHTMLに差し込んで出力する
5. 開き方を案内し、フィードバックで更新する

---

## ステップ1: 論点を抽出する（生素材の場合のみ）

`../extract-issues/SKILL.md` を Read し、その手順（論点候補の洗い出し → 型分類と属性付け → 中核概念の探索 → 事実と判断の分離）に従って論点を抽出する。コンソールへの一覧出力は省略してよい（このスキルではHTMLが成果物）。ただし**中核の問い・型・決定者・ステータス・依存関係・根拠の有無**は後のステップで必要になるので必ず揃えること。

抽出済みの論点一覧を渡された場合は、上記の属性が欠けていないか確認し、欠けていれば素材から補完するかユーザーに確認する。

## ステップ2: ツリー構造に編成する

イシューツリーの編成ルール：

- **ルートは中核の問い**（1文）。extract-issues で言う「中核の問い」をそのまま使う
- **各ノードは問いの形**にする（「〜すべきか」「〜はどうなっているか」）。名詞の羅列（「エラー処理」）にしない
- **子は親の分解**：子ノード群に全部答えると親の問いに答えられる、という関係を保つ。単なるグルーピングやカテゴリ分けをツリーにしない
- **分解の軸を明示する**：ある親の子どもたちは同じ軸で割る（例:「どこで失われるか」→ BE／FE、「どう直すか」→ 方式A／方式B）。軸はノードの `axis` として記録し、HTML上で「〜で分解」と表示される
- **MECEチェック**：各分解について「漏れはないか（他に子はないか）・ダブりはないか（2つの子が同じ話をしていないか）」を自問する。完全なMECEが無理な場合は、漏れの可能性をノードの詳細に ⚠️ として書く
- **深さは用途で使い分ける**。意思決定マップとしては2〜4階層が目安（1画面で骨格が掴めることを優先し、細部は詳細欄の選択肢・判断材料に落とす）。調査結果・実装計画の網羅的な構造化では深くてよい — テンプレートは任意の深さに対応し、大きなツリーは初期表示で2階層に自動で畳まれ、検索・子孫数表示で迷子にならない。深さを理由にテンプレートを避けない
- **依存関係はツリーと別に持つ**（`deps`）。「事実確認 → Dev方針・トレードオフ → PO決定 → 実行計画」の依存はツリーの親子とは別の軸なので、ノード属性として記録する（HTML上でリンクになる）
- 中核概念（共通言語）が見つかっている場合は、ツリーとは別枠の説明カードとして扱う（`concept`）

## ステップ3: データJSONを作る

以下のスキーマでJSONを作る。**すべてのテキストはプレーンテキスト**（HTMLタグ・Markdown記法は不可。表示側でエスケープされずそのまま文字として出る）。

```json
{
  "theme": "テーマ（ページタイトルになる）",
  "coreQuestion": "中核の問い（ルートノードの本文）",
  "sources": "素材の説明（例: pbi/642/README.md + draft/v3 一式）",
  "types": [
    { "name": "型名（例: 事実／仮説／棄却済み）", "color": "CSS色（省略可。省略時は組込パレットから順に割当）" }
  ],
  "concept": {
    "name": "中核概念の名前（例: 区分A/B）",
    "note": "一言説明",
    "rows": [
      { "label": "区分A", "definition": "定義", "criterion": "判別基準" }
    ]
  },
  "nodes": [
    {
      "id": "1",
      "type": "事実確認",
      "title": "ノードの短いタイトル（ツリーに表示、25字以内目安）",
      "question": "問いの完全な形（1文）",
      "status": "調査中",
      "decider": "Dev",
      "axis": "子ノードの分解の軸（子がいる場合のみ）",
      "why": "なぜ論点か（対立軸・一長一短・認識が割れる点）",
      "options": [
        { "label": "案a（現状維持を含める）", "note": "補足・代償" }
      ],
      "evidence": [
        { "text": "判断材料・事実", "source": "file:line や文書名", "verified": true }
      ],
      "decision": { "choice": "採択した案", "reason": "採択理由", "date": "2026-07-31" },
      "deps": ["2"],
      "children": []
    }
  ]
}
```

制約：

- `types` は任意。**省略時**は `type` を `事実確認` / `Dev方針` / `PO決定` / `トレードオフ` / `実行計画` の5型（extract-issues の型）から選ぶ。**宣言時**は各ノードの `type` を宣言した型名から選ぶ。素材が意思決定の論点なら省略（デフォルト5型）、調査結果や実装計画の構造化なら素材に合う型を宣言する（例: 調査なら `事実／仮説／棄却済み`、計画なら `決定済み方針／未決事項／作業`）。型は多くても6個程度に絞る（凡例とフィルタが機能する数）
- `status` は `未着手` / `調査中` / `材料揃い` / `決定済み` のいずれか
- `id` はツリー全体で一意（`1`, `1-1`, `2` のような階層番号を推奨）
- `deps` は依存先ノードの `id` の配列。存在しない id を書かない
- `concept` は無ければ `null`
- `verified: false` の判断材料は ⚠️ 付きで表示される。未確認のものを `true` にしない
- `decision` はユーザーが決定を下した論点にのみ書く（採択案・理由・決定日）。書いたら `status` も `決定済み` にする
- 任意項目（`axis` / `why` / `options` / `evidence` / `decision` / `deps` / `decider`）は無ければ省略してよい

## ステップ4: HTMLを生成する

1. このスキルの `assets/tree-template.html` を Read で読み込む
2. テンプレート中の `__TITLE__`（1箇所）をテーマ名に、`__DATA__`（1箇所）をステップ3のJSONに置き換える
3. 出力先に Write する
   - ユーザー指定があればそのパス
   - 指定がなければ素材と同じディレクトリに `issue-tree.html`（素材がディレクトリなら その直下）。貼り付け素材などでファイルの置き場が自明でない場合のみ、保存先をユーザーに確認する
4. 生成後、`node --check` 相当の検証はできないため、少なくともJSONが正しいこと（`python3 -c "import json,sys; json.load(open(...))"` 等で機械検証。HTMLに埋め込む前のJSON文字列を一時ファイルで検証するとよい）を確認する

## ステップ5: 報告と更新

- 出力パスと、**ブラウザで開くための URL・コマンドの両方**を報告する：
  - **URL**: `file:` 形式で必ず併記する（ターミナルからクリックで開けるようにする）。WSL では `wslpath -w` の結果が UNC パス（`\\wsl.localhost\...`）になるため、`\` を `/` に置換してから `file:` を前置する。以下のコマンドで生成できる：

    ```bash
    echo "file:$(wslpath -w <パス> | tr '\\' '/')"
    # 例: file://wsl.localhost/Ubuntu-24.04/home/.../issue-tree.html
    ```

    WSL 以外では `file://<絶対パス>`（例: `file:///Users/.../issue-tree.html`）でよい
  - **コマンド**: `wslview <パス>` または `explorer.exe "$(wslpath -w <パス>)"`（WSL）、`open <パス>`（macOS）、`xdg-open <パス>`（Linux デスクトップ）のうち環境に合うもの
- ツリー全体の要約（ノード数・型の内訳・未決論点の数）を1〜2文で添える

### 更新手順（抽出 → 検証 → 再埋め込み）

フィードバック（論点の追加・分解の組み替え・ステータス更新・調査結果の反映）を受けたら、HTML内の `const DATA = ...` を直接 Edit するのではなく、次の手順で更新する。HTMLは常に1ファイルで自己完結し続ける（sidecar ファイルは残さない）：

1. HTML から `const DATA = {...};` の JSON 部分を機械的に抽出し、scratchpad に一時 JSON ファイルとして保存する
2. 一時 JSON を編集し、`python3 -c "import json; json.load(open('...'))"` で機械検証する
3. 検証済み JSON を HTML の `const DATA = ` 部分に再埋め込みして Write する

テンプレート由来の部分（スタイル・スクリプト）は編集しない。テンプレートが改善された場合も、この抽出→再埋め込みで既存ツリーを新テンプレートに載せ替えられる。

### 決定の反映

生成後、ユーザーは会話の中で論点を1つずつ決定していくことが多い（「案aでOKです」等）。決定を受けたら**その都度**上記の更新手順で反映する：

- 該当ノードの `status` を `決定済み` に、`decision` に採択案・理由・決定日を記録する
- 決定によって不要になった選択肢・下位論点は消さずに残す（`decision` があれば読み手は経緯ごと追える）
- **ソースの markdown（plan.md・調査ドラフト等）がある場合は、ツリーと markdown の両方に同時に反映する**。片方だけ更新して乖離させない。どちらを正とするか迷ったらユーザーに確認する

## 注意点

- **ツリーの見た目より分解の質が本体**。カテゴリ分けをツリーにしただけのもの（子に全部答えても親に答えられない）は作り直す
- ノードの `title` は意思決定者が読める言葉にする（実装用語だけの表現は詳細欄に置く）
- **意思決定マップ用途**では、大きすぎるツリー（ノード30個超）は俯瞰できなくなる。下位の細部は詳細欄に畳み込み、ツリーは意思決定の骨格に絞る。**調査・計画の構造化用途**ではノード数・深さの上限は設けない（初期折りたたみ・検索・子孫数表示で俯瞰性は保たれる）
- 結論を出さない。ツリーは判断材料の地図であり、推奨を書く場合は詳細欄で「推奨」と明示して根拠を添える
- 共有目的で claude.ai の Artifact として公開したいと言われた場合のみ、同じHTMLを Artifact ツールで公開する（デフォルトはローカルファイルのみ）
