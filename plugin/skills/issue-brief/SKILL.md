# 論点ブリーフスキル（issue-brief）

大部の資料をレビューするとき、いちばん大変なのは指摘を書くことではなく「**この資料の論点は何で、どこで何が主張されていて、どれを検証すべきか**」を把握することです。このスキルはその把握を肩代わりし、レビュアーが検証と判断に集中できる**ブリーフ（レビューの地図）**を作ります。

このスキルは**レビューをしません**。指摘・評価はレビュアー（またはレビュー系スキル）の仕事で、その入力を整えるのがこのスキルの仕事です。

同プラグインの `extract-issues` スキルと役割を分担しています：

- `extract-issues` … 任意の素材から論点を抽出・構造化する（汎用）
- `issue-brief` … レビューという用途に特化し、論点把握＋裏取り計画＋レビュー観点までを一式で出す。論点抽出の手順は extract-issues のものを内部で使う

## 入力

```
# Claude Code（ybaba プラグイン経由）
/ybaba:issue-brief <レビュー対象（ディレクトリ・ファイル群）> <元チケット（PBI等）>

# OpenAI Codex CLI
$ybaba:issue-brief <レビュー対象> <元チケット>    # marketplace 経由のプラグイン
$issue-brief <レビュー対象> <元チケット>          # ~/.agents/skills/ fallback 導入時
```

- **レビュー対象**（必須）: スパイク調査ドラフト（`draft/vN/` 一式）、design-doc、提案書など
- **元チケット**（推奨）: PBI・チケット・依頼文。資料が答えるべき問いの出どころ。無い場合はその旨を確認し、diff 分析（ステップ3）を省略した縮小版ブリーフになることを伝える
- レビューの観点・重点（任意）: ユーザーが指定した場合はブリーフの力点に反映する

## 全体の流れ

1. 元チケットから論点を**独立導出**する（資料を読む前に）
2. 資料を読み、論点を**逆抽出**する（章→論点トレーサビリティ）
3. 両者の **diff** を取る（漏れ・すり替え・非論点）
4. **裏取りチェックリスト**を作る（検証すべき主張の抽出と優先度付け）
5. **論点別レビュー観点**を付けて、ブリーフとして出力する

ステップ1〜3の論点抽出の詳細手順（論点候補の基準・5つの型・属性付け・リンティング）は、`../extract-issues/SKILL.md` を Read して、その順抽出／逆抽出／突き合わせモードの手順に従うこと。以下では issue-brief 固有の点だけ述べる。

---

## ステップ1: 元チケットから論点を独立導出する

**順序が重要**。先にレビュー対象を読むと、資料の立てた論点に引っ張られて「漏れ」を検出できなくなる（アンカリング）。必ず元チケットだけを先に読み、extract-issues の順抽出の手順で「この資料が答えるべき論点」を導出してから、レビュー対象を開く。

- チケットが**名指しした問い・調査起点・完了条件**は、番号付きで全件リスト化する（ステップ3で消化状況を突き合わせる）
- すでにレビュー対象を読んでしまっている場合は、チケットの記述**だけ**を根拠に再導出し、その旨をブリーフに明記する

## ステップ2: 資料から論点を逆抽出する

レビュー対象を通読し、extract-issues の逆抽出の手順で以下を作る：

- **資料が立てている論点の一覧**（型・決定者・資料内での結論・ステータス）
- **章→論点トレーサビリティ表**（各章がどの論点を扱い、何を結論し、根拠があるか）
- どの論点も扱っていない章、どの章にも現れない論点があれば記録する

資料が巨大な場合は章ごとに処理して統合する。読み飛ばした部分は必ず申告する。

## ステップ3: diff を取る（漏れ・すり替え・非論点）

ステップ1の独立導出とステップ2の逆抽出を突き合わせ、3分類で整理する：

- **漏れ**: チケットが求めているのに資料が論点として立てていない（名指しされた調査起点・完了条件の未消化を含む）
- **すり替え**: 立っている論点が元の問いと微妙にズレている（例: 「どう伝えるか」を問われて「どう実装するか」だけ答えている）
- **非論点**: 論点として立っているが、実は確定済みの制約や単なる事実

これは**指摘ではなく検証候補**。「漏れの可能性がある。○章に暗黙に含まれているかをレビューで確認」のように、レビュアーが確かめる問いの形で書く。

## ステップ4: 裏取りチェックリストを作る

資料中の**事実主張**を抽出し、レビューで実コード・実データ検証すべきものを優先度付きで一覧化する。

**抽出対象**（優先度の高い順）：

1. **結論を支えている主張** — これが崩れると資料の結論が変わるもの（各論点の判断材料の中核）
2. **断定している主張** — 「必ず」「〜しかない」「全て」「唯一」など強い限定。反例が1つあれば崩れる
3. **根拠の粒度が粗い主張** — `file:line` がない、伝聞・推測の可能性がある、⚠️なしで未確認事項を書いている疑いがあるもの
4. **数値・件数** — 「N件のエラーコード」「M箇所で使用」など。数え直しで検証できる

各項目には**検証方法**を添える（例: 「`<file>:<line>` を開いて分岐条件を確認」「`grep <code>` で使用箇所を数え直す」）。全件の裏取りが現実的でない場合に備え、優先度1・2を「必須」、3・4を「抜き取り推奨」と区別する。

## ステップ5: ブリーフを出力する

`assets/brief-template.md` を Read で読み込み、そのフォーマットに従って**コンソールに全文出力**する。構成：

1. **資料の主張の要約** — 資料が「何を結論した資料なのか」を3行以内で。レビュアーが最初に掴むべき全体像
2. **推奨する読み順** — 論点の依存関係（事実→方針→決定→計画）に基づく。資料の章順と読むべき順が違う場合に価値が出る
3. **論点マップと論点一覧** — extract-issues の形式
4. **章→論点トレーサビリティ表**
5. **diff（漏れ・すり替え・非論点）** — 検証候補の問いの形で
6. **裏取りチェックリスト** — 優先度・検証方法付き
7. **論点別レビュー観点** — 各論点に対しレビュアーが問うべき質問。定型観点：
   - 判断材料は決定者が判断できる形で揃っているか（実装用語のままになっていないか）
   - 選択肢に現状維持が含まれているか
   - 事実と判断が分離されているか（断定できないものを事実として書いていないか）
   - 依存する事実が未確定のまま方針・決定に進んでいないか

ファイルには保存しない。**ユーザーが保存先を指定した場合のみ**（例: `pbi/642/review/brief.md`）そのパスに保存する。

## ステップ6: レビューへの接続

出力後、ユーザーに次の進め方を確認する：

- レビュアー（人間）がブリーフを持ってレビューする → ここで完了
- 続けてこのセッションでレビューまで行う → 裏取りチェックリストの「必須」から着手し、検証結果（✅/❌）を表に埋めてから指摘の作成に進む。指摘のフォーマットはユーザーのレビュー系スキル・慣行に従う

---

## 注意点

- **ブリーフに評価を書かない**。「この論点の扱いは不十分」ではなく「この論点の判断材料が揃っているかを確認」と書く。評価はレビューの仕事
- **独立導出の汚染を避ける**。ステップ1を飛ばして資料から読み始めない。読んでしまったら申告する
- diff の「漏れ」は資料の欠陥と決めつけない。意図的なスコープ外の可能性があるため、資料側にスコープ外の宣言がないかを先に探し、あればその旨を添える
- 元チケットが無い・簡素すぎる場合、diff 分析は弱くなる。その限界をブリーフ冒頭に明記する
