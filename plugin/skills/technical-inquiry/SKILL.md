# 技術探究スキル（technical-inquiry）

「どう作るか」が決まらない状態（方式が選べない、原因が分からない、実現できるか分からない）を、**仮説を立て、反証条件を先に書き、最短で壊しに行き、観測で確信度を更新し、可逆性に見合う確信度で決める** ループで解消します。成果物は探究ログ 1 本で、その中心は仮説ボードです。

このスキルが守る 3 つの規律：

1. **反証条件を、調べる前に書く。** 調べた後に書くと、結果に合わせて条件が緩みます。
2. **確信度で持つ。** 仮説を 0/1 で扱わず、観測が増えるたびに更新し、「まだ分からない」を正規の状態として扱います。
3. **可逆性で決める。** 戻せる判断は低い確信度で決めてよく、戻せない判断は高い確信度を要求するか、先に戻せる形にします。これが「調査をいつ終えるか」の唯一の原理的な根拠です。

役割分担：**ホスト**（このスキルを実行しているエージェント）が仮説ボードを所有し、問いの設定・確信度の更新・統合・ユーザーとの対話を行う。**サブエージェント**（Herdr の別タブ）は対立仮説の生成・kill テストの実行・プレモーテムを担い、観測だけを返す。**決めるのはユーザー。**

## 入力

```
# Claude Code（ybaba プラグイン経由）
/ybaba:technical-inquiry <問い・資料> [--out <探究ログの保存先>] [--mode select|cause|feasibility]
                         [--challenger claude|codex] [--challenger-model <モデル>] [--rounds N]
                         [--agent-args "<引数>"] [--no-subagents] [--close]

# OpenAI Codex CLI
$ybaba:technical-inquiry <問い・資料> [...]    # marketplace 経由のプラグイン
$technical-inquiry <問い・資料> [...]          # ~/.agents/skills/ fallback 導入時
```

| オプション | 既定値 | 意味 |
| --- | --- | --- |
| `<問い・資料>` | 必須 | 技術的な問いの文、design-doc のパス、スパイク PBI、観測事実（ログ・メトリクス・再現手順）。複数可 |
| `--out` | なし | 探究ログの保存先。**未指定なら開始前に質問する**（design-doc と同じ方針。既定の保存先や命名規則を持たない） |
| `--mode` | 自動判定 | `select`＝方式選定、`cause`＝原因究明、`feasibility`＝実現可能性。判定結果は着手前に確認する |
| `--challenger` | `claude` | 対抗役（仮説生成・プレモーテム）のエージェント種別。`codex` にすると系統を変えて盲点の相関を減らせる |
| `--challenger-model` | claude なら `claude-opus-5-5`、codex なら codex の既定 | 対抗役のモデル |
| `--rounds` | 3 | ステップ4 の探究ループの最大ラウンド数。停止条件を満たせば早く終わる |
| `--agent-args` | なし | サブエージェント起動時に追加で渡す引数（例: `--permission-mode acceptEdits`）。**ユーザーが明示したときだけ**付ける |
| `--no-subagents` | なし | ホスト単独で回す。Herdr 外や軽い探究向け。独立性が落ちることをログに明記する |
| `--close` | 付けない | 終了時にこのスキルが作ったタブを閉じる。既定は残す |

「codex を対抗役に」「opus の xhigh で」のようにプロンプト中で自然に指定されていれば、それをオプションとして扱う。

## 3 つのモード

| モード | 問いの形 | 仮説の種別 | kill 条件の典型 | 決定の形 |
| --- | --- | --- | --- | --- |
| **方式選定** `select` | 「不変条件を満たしつつ X するには、どの方式か」 | 方式仮説：「方式 A は条件 C の下で不変条件を満たす」 | 「A でも条件 C で不変条件 I を破るなら不採用」 | 採用案（または統合案）と棄却理由 |
| **原因究明** `cause` | 「観測された事象 E はなぜ起きているか」 | 原因仮説：「E の原因は R である」 | 「R が原因なら観測 O が出るはず。出なければ棄却」 | 原因の特定と、修正の方向。修正そのものはスコープ外 |
| **実現可能性** `feasibility` | 「制約 C の下で X は実現できるか」 | 実現仮説：「X は手段 M で C を満たして実現できる」 | 「M で X を試み、制約 C のどれかを破るなら不可」 | 可・不可・条件付き可と、その条件 |

モードは入力から推定し、保存先の質問と一緒にユーザーに確認する。1 つの探究に複数モードが混ざるときは、原因究明 → 方式選定 の順に分けて回す。

## 全体の流れ

1. **問いを立てる** — 中核の問い、不変条件、前提の棚卸し、分解、現状の事実
2. **仮説を立てる** — 対抗役に盲検で候補を出させ、ホストの候補と統合し、初期確信度を付ける
3. **反証条件を先に書く** — 仮説ごとに kill 条件と判別テストを事前登録する。**ここまで調査禁止**
4. **調べて更新する** — 仮説ごとの kill テストを並列に走らせ、観測を回収し、ホストが一括で確信度を更新する。停止条件まで繰り返す
5. **統合して決める** — 対立の根、システムへの影響、可逆性と閾値、プレモーテム、比較。推奨を添えてユーザーが決める
6. **記録して渡す** — 決定記録、リント、design-doc への引き渡し、TL;DR

ユーザーに確認を取るのは原則 3 回：ステップ1 の終わり（問い・不変条件・前提）、ステップ3 の終わり（ボードと反証条件）、ステップ5（決定）。ラウンドの合間は短い報告だけで進める（止めてほしければユーザーがそう言う）。

## ステップ0: 前提と入力を確認する

```bash
test "${HERDR_ENV:-}" = 1 && echo "in herdr: workspace=$HERDR_WORKSPACE_ID"
herdr agent start --help | grep -q -- '--kind' && echo "herdr 0.8+"
```

- 入力をすべて読む。design-doc が渡された場合、Scope / Background / ProblemStatement は問いの材料にする。**Proposal があれば「ユーザーの本命案」として扱い、ステップ2 の対抗役には見せない**
- モードを推定する
- 保存先を `--out` または本文から読み取る。読み取れなければ質問する
- `HERDR_ENV` が `1` でなければ、`--no-subagents`（ホスト単独）で続けるか中断するかを聞く。Herdr の外から Herdr を操作しない
- 以上の質問（保存先・モード・Herdr 外の扱い・内容の不明点）は **1 回にまとめて聞く**
- 探究のテーマ名を英小文字ケバブケースで短く決める（例: `queue`、`slow-search`）。サブエージェントのタブ名 `ti-<テーマ>-<役割>` に使う。32 文字以内に収まるよう短くする
- `assets/inquiry-log-template.md` を Read し、その形式で保存先に探究ログを作る。以後、各ステップとラウンドの終わりにログを保存する（再開に備える）

指定された保存先に既にファイルがある場合は、**再開**として扱う：ログを読み、仮説ボードと事前登録済みの反証条件を引き継ぎ、止まっていたステップから続ける。上書きの確認は不要（同じ探究の続き）。別の探究を同じパスに書こうとしている場合だけ確認する。

## ステップ1: 問いを立てる

`assets/question-bank.md` を Read し、「不変条件」「前提を崩す問い」の節を使う。

### 1-1 中核の問い

How の形で 1 文にする。「〜を満たしつつ〜するには、どの方式／原因／条件か」。ユーザーの生の言葉を引用できるようにしておく。

### 1-2 不変条件

絶対に守るべき条件だけを列挙する。「今こう作っているから」ではなく「本当に必要なのは何か」まで戻す（例:「予約が失われない」「X 秒以内に処理される」「二重課金しない」「既存クライアントを壊さない」「月額コスト上限」）。

- 各条件に**出典**（誰が決めた・どこに書いてある）と、**検証可能な形**（指標・閾値）を付ける
- 出典の無い条件は不変条件ではなく「前提候補」として 1-3 に回す

### 1-3 前提の棚卸し

「〜は変えられない」「〜でなければならない」「今こうなっている」を列挙し、1 つずつ問う：**誰の制約か／いつ決まったか、今も成り立つか／固定か可変か／外したら最悪何が起きるか／それは制約か好みか**。

- 可変と分かった前提は制約から外し、探索空間に戻す（ステップ2 の候補が増える）
- 固定と確認できた前提は不変条件に昇格させる（出典を付ける）
- 判断がユーザーに要るものは「要確認」として確認事項に載せる

### 1-4 分解

中核の問いを、独立に答えられる部分問いに分ける。依存順（事実 → 方式 → 選択）に並べる。部分問いが 1 つしかないなら分解しない。

### 1-5 現状の事実

コードが今何をしているかを確認する。事実には `file:line` を付け、ID（F1, F2, …）を振る。

- 対象が 1〜2 ファイルならホストが自分で読む
- 対象が複数モジュールに跨るなら、`assets/subagent-briefs.md` の「事実棚卸し」ブリーフで `ti-<テーマ>-facts` タブに任せる（読み取り専用、Opus 5.5 / effort medium）
- 原因究明モードでは、観測事象（ログ・メトリクス・再現条件）もここで事実として整理する

### 確認

1-1〜1-5 をログの「1. 問い」に書き、ユーザーに確認する。特に不変条件と前提の仕分けはユーザーの判断が要ることが多い。

## ステップ2: 仮説を立てる

### 2-1 対抗役に盲検で候補を出させる（先に出す）

`ti-<テーマ>-hypo` タブに `--challenger` のエージェントを立て、`assets/subagent-briefs.md` の「盲検仮説生成」ブリーフを送る。**渡すのは中核の問い・不変条件・現状の事実・観測事象だけ。** ホストの候補、design-doc の Proposal、ユーザーの本命、確信度は一切含めない。これを守らないと対抗役はホストの考えを確認して返してくるだけになる。

### 2-2 ホストも並行して候補を書く

対抗役を待つ間に、ホストも候補を手元に書く（まだログには書かない）。

### 2-3 統合する

- 重複をまとめ、各仮説に **出自**（ユーザー／ホスト／対抗役）を記録する
- **対立仮説が 1 つ以上あること**を確認する。全候補が同じ方向を向いていたら、対抗役に「これら以外で、前提の 1 つを外した候補を」と追加依頼する
- 方式選定では **現状維持** を必ず候補に含める。含められない理由があるなら、それを判断材料に書く
- 原因究明では **説明表**（観測 × 仮説：○説明できる／×できない／△条件付き）を作る。説明できない観測を持つ仮説は、その観測が最初の kill テスト候補になる

### 2-4 初期確信度を付ける

- 10% 刻みの粗い数値。精度を主張しない
- 根拠欄に何に基づくかを書く。観測が無ければ「事前の見立て」と明記する。どう見立ててよいか分からなければ数値を置かず **「未評価」** と書く
- 原因究明の仮説は互いに競合するので合計がおおむね 100% になるように、方式選定・実現可能性の仮説は独立に成立しうるので個別に付ける

仮説ボードをログの「2.」に書く。ユーザー確認はステップ3 とまとめて行う。

## ステップ3: 反証条件を先に書く

`assets/question-bank.md` の「kill 条件の書き方」「判別テストの手段」を使う。仮説ごとに次を書く。

| 項目 | 要件 |
| --- | --- |
| **kill 条件** | 「これが観測されたら棄却」を **指標・閾値・条件** の 3 要素で書く。「うまくいかなければ」は不可。例:「ピーク相当 500 req/s で p95 が 2 秒を超えるなら不採用」 |
| **判別テスト** | kill 条件を評価する最安の手段（ソース読解 → 既存ログの突合 → 再現スクリプト → ミニ実装 → ベンチ の順にコストが上がる）。1 つのテストで複数の仮説を判別できるなら優先する |
| **情報価値チェック** | 「結果がどちらに転んでも判断は同じか」を問う。同じなら、そのテストはやらないか、判断が変わる形に設計し直す |
| **想定コスト** | 時間の目安。ラウンド割り当てに使う |
| **優先度** | 情報価値 ÷ コスト。確信度が高い本命を壊しに行くテストほど情報価値が高い |

- 「動くことを確かめる」形のテストは「どの条件で動かなくなるか」の形に言い換える
- ログの「3. 反証条件の事前登録」に **登録日時** を入れる。以後 kill 条件を変える場合は変更履歴に理由付きで残す。結果を見てから緩めない
- ここまで、ステップ1-5 の事実確認を除き **仮説を試す調査をしていないこと** を確認する

### 確認

ボードと反証条件をまとめてユーザーに見せ、仮説の過不足・kill 条件の妥当性・優先度を確認する。

## ステップ4: 調べて更新する（探究ループ）

1 ラウンド＝「テストを選ぶ → 並列に実行する → 全部回収する → ホストが一括で更新する → 停止判定」。最大 `--rounds` 回。

### 4-1 テストを選ぶ

優先度順に、このラウンドで回すテストを選ぶ。本命を壊しに行くテストを後回しにしない。

### 4-2 実行する

- 数コマンドで済むテスト（grep で数える、設定値を読む）はホストが自分でやる。サブエージェントを立てる方が高くつく
- それ以外は **仮説 1 つにつき 1 タブ** `ti-<テーマ>-h<N>` で、`assets/subagent-briefs.md` の「kill テスト」ブリーフを送る。同じ仮説の再テストは同じタブに続けて頼む（タブ＝仮説の履歴になる）
- 測定型（走らせて閾値と比べる）は Opus 5.5 / effort medium、判断型（曖昧なログの解釈、原因の追跡）は effort high
- 実験ファイルは scratchpad 配下 `ti-<テーマ>/h<N>/` にだけ作らせる。リポジトリは変更させない
- 同じ環境資源（同じ DB、同じポート）を奪い合うテストは並列にしない
- 送信は `--wait` 無しで全員に送り、その後 1 つずつ `herdr agent wait` する。`blocked` になったら画面を読んでユーザーに提示し、指示に従う（herdr-subagent スキルの規則）

### 4-3 回収する

各タブの返答から **観測だけ** を取り出し、ID（O1, O2, …）を振ってログの「4. ラウンド N / 観測」に転記する。

- サブエージェントが確信度・推奨・修正案を書いてきても採用しない。観測だけ採る
- **決定を変えうる観測は、ホストが根拠（file:line・数値）を自分で開いて確認する。** 確認できないものは ⚠️ を付ける
- 「想定外の観測」は新しい仮説の候補として扱う。テストする前にステップ2〜3 を通す（kill 条件を先に書く）

### 4-4 一括で更新する

全テストの観測が揃ってから、仮説ごとに「前 → 後」と「根拠となる観測 ID」を書く。1 件ずつ更新しない（先に来た結果に後の解釈が引きずられる）。

- 観測の無い仮説の確信度は動かさない
- kill 条件に該当した仮説はステータスを「棄却」にする。確信度は 0 にせず低い値を残してよい（観測が誤っている可能性のぶん）
- 判定不能だったテストは、何が足りなかったかを記録し、別の手段で再設計するか諦めるかを決める

### 4-5 停止判定

次のいずれかで止める：

| 条件 | 意味 | 次 |
| --- | --- | --- |
| 残った仮説の kill 条件をすべて評価した | 調べられることは調べた | ステップ5 へ |
| 残る不確実性が決定を変えない | 情報価値がゼロ | ステップ5 へ |
| `--rounds` に達した | タイムボックス | ユーザーに 3 択を提示：今の確信度で決める／可逆化して決める／待つ（待つコストを明記） |

ラウンドの終わりに、更新後のボードの要約（変わった仮説だけ）を短く報告して次へ進む。

## ステップ5: 統合して決める

`assets/question-bank.md` の「システム思考」「可逆性」「統合」の節を使う。

### 5-1 対立の根

残った候補が対立するなら、「どの前提が成り立つと A、どう違うと B か」を書く。対立の根にある共有前提が見つかれば、両方を満たす統合案や条件分岐（「条件 C なら A、そうでなければ B」）が出ることがある。統合案は新しい仮説としてボードに足し、**kill 条件を付けてから**採用候補にする。**折衷（中間案）は統合ではない。**

### 5-2 システムへの影響

採用候補ごとに、上流・下流への影響、バックプレッシャー、フィードバックループ、遅延、局所最適（詰まりが別の場所へ移るだけでないか）を見る。影響が不変条件に触れるなら、それは kill 条件の見落としなので 3 に戻って追加する。

### 5-3 可逆性と閾値

| 可逆性 | 定義 | 決定に必要な確信度の目安 |
| --- | --- | --- |
| **二方向** | 戻すのに追加コストがほぼ無い（設定・フラグ・コード変更で戻る） | 60% 以上 |
| **一方通行** | 戻すのにデータ移行・外部契約の変更・長い併存期間が要る | 90% 以上、**または先に二方向にする** |

一方通行の候補には、可逆化の手段（フラグ、アダプタ層、新旧併存、最終責任時点まで決定を遅らせる）を先に検討し、可能なら採用候補をその形に書き換える。閾値は目安であり、ユーザーと合意して変えてよい。変えた場合は理由をログに書く。

### 5-4 プレモーテム

`ti-<テーマ>-premortem` タブに対抗役を立て、`assets/subagent-briefs.md` の「プレモーテム」ブリーフを送る。渡すのは **採用候補の内容・不変条件・現状の事実だけ**。ホストが推す理由、ボード、棄却案は渡さない。

返ってきた失敗理由を 3 つに仕分ける：

- **評価済み** — 既存の kill 条件で評価した観測がある → その観測 ID を添える
- **未評価** — 新しい kill 条件の候補 → もう 1 ラウンド回すか、残リスクとして決定記録に書くかをユーザーに聞く。**一方通行の判断なら未評価を残したまま決めない**
- **不採用** — 不変条件やスコープに照らして外れている → 理由を書く

二方向の判断ではプレモーテムを省略してよい。省略した場合はその旨を書く。

### 5-5 比較と推奨

| 候補 | コスト | 成功確率（＝確信度） | 失敗時損失 | 可逆性 | 待つコスト | 備考 |

推奨を 1 つ、理由付きで書く。**決定はユーザー。** 決定・保留・差し戻し（もう一周）のどれかを受け取る。

## ステップ6: 記録して渡す

### 6-1 決定記録

ログの「6. 決定記録」に書く：決定／根拠（観測 ID を引く）／棄却した案と理由／**覆す条件**（何が観測されたらこの決定を見直すか。観測可能な形で）／未解決・残リスク／次の一手。

### 6-2 リント

`ti-<テーマ>-lint` タブに `assets/subagent-briefs.md` の「リント」ブリーフを送る（Opus 5.5 / effort low。`--no-subagents` ならホストが同じ項目を自分で点検する）。❌ が返った項目はログを直してから次へ進む。

### 6-3 引き渡し

ログの「7. 引き渡し」に、design-doc の Proposal に流し込める抜粋（提案する変更／設計判断／検討した代替案とその棄却理由／リスク・注意点）を書く。続けて使えるスキルを案内する：

- `design-doc` — Proposal をこの抜粋で書く・更新する
- `design-policy` — 採用案を 5 軸で評価する
- `design-story-telling` — 採用案をシナリオで動かして反証する（探究ループの延長として使える）
- `delivery-guide` — 実装ガイドに落とす

### 6-4 保存と報告

保存先にログを書き出し、保存先のパスを 1 行で示したうえで全文をコンソールに出力する。返答は必ず **TL;DR** で締める。

```

- 問い: <中核の問いを 1 行>
- 決定: <採用案>（確信度 <N>%、可逆性: 二方向／一方通行）
- 決め手になった観測: <観測 ID と要点を 1〜2 行>
- 棄却した案: <案と理由を 1 行ずつ>
```

## 行動規則

哲学や方法論の名前は SKILL.md の中だけの話で、**出力には書かない**。出力は「不変条件・前提・仮説・反証条件・観測・確信度・可逆性・判断」の実務語彙で書く。

- **反証条件を書く前に、仮説を試す調査を始めない。** 事実確認（1-5）だけが例外
- **対抗役にホストの仮説・ユーザーの本命・確信度を見せない。** 盲検が崩れたら、その旨をログに書く
- **確信度を 0/1 で書かない。「未評価」を許す。** 10% 刻みで、精度を主張しない
- **更新には観測 ID を添える。** 観測の無い更新をしない。1 件ずつ更新せず、ラウンドの観測が揃ってから一括で更新する
- **判別力のないテストをやらない。** 結果がどちらでも判断が変わらないなら設計し直す
- **統合を折衷にしない。** 対立の根にある前提を問う
- **一方通行の判断にはプレモーテムを必須にする。** 未評価の失敗理由を残したまま決めない
- **サブエージェントは観測を返す。** 確信度・推奨・修正案を書かせない。書いてきたら無視して観測だけ採る
- **ホストがボードを持つ。** サブエージェントにログを編集させない。リポジトリも変更させない
- **決定を変える観測はホストが裏取りする。** 確認できなければ ⚠️
- **決めるのはユーザー。** 推奨は添えてよい

## 注意点

- **Herdr の外から操作しない**：`HERDR_ENV=1` を確認する。外なら `--no-subagents` で回すか中断する
- **タブは `tab create --workspace "$HERDR_WORKSPACE_ID" --no-focus`、1 タブ 1 エージェント、ID は JSON 応答から取る**（herdr-subagent スキルの規則をそのまま守る）
- **ダイアログに勝手に答えない**：`blocked` は画面を読んでユーザーに提示する。削除・push・外部送信の承認を自分で判断しない
- **`--agent-args` は言われたときだけ**：権限モードの緩和はユーザーの明示が要る。並列の kill テストで承認待ちが頻発するなら、`--agent-args "--permission-mode acceptEdits"` 等を提案してよいが勝手に付けない
- **実験は scratchpad で**：リポジトリ内にファイルを作らない。サブエージェントが変更してしまった場合は `git status --short` で確認してユーザーに報告する
- **閉じてよいのはこのスキルが作ったタブだけ**：他のタブ・ペイン・ワークスペースに触らない
- **巨大な探究は分割する**：仮説が 8 個を超えるなら、分解（1-4）に戻って部分問いごとに探究を分ける
- **再開に備える**：ログは常に最新の状態で保存しておく。ラウンドごとに保存する
