# サブエージェントの役割・起動・ブリーフ（technical-inquiry）

ホストが仮説ボードを所有し、サブエージェントは観測だけを返す。この分担を守るための役割表・起動手順・ブリーフ固定文・返答フォーマットをまとめる。起動の細部（エラー時の扱い、`blocked` の対応、後方互換）は herdr-subagent スキルに従う。

## 役割表

| 役割 | タブ名 | 使う場面 | 盲検（渡さないもの） | kind | モデル | effort | タイムアウト目安 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 事実棚卸し | `ti-<テーマ>-facts` | ステップ1-5。対象が複数モジュールに跨るとき | 仮説は渡さない（事実だけ集める） | claude | `claude-opus-5-5` | medium | 10 分 |
| 盲検仮説生成 | `ti-<テーマ>-hypo` | ステップ2-1。毎回 | ホストの候補・ユーザーの本命・design-doc の Proposal・確信度 | `--challenger` | `--challenger-model` | high（難しい原因究明は xhigh） | 10 分 |
| kill テスト | `ti-<テーマ>-h<N>` | ステップ4-2。仮説 1 つにつき 1 タブ | 他の仮説・ボード・ホストの確信度 | claude | `claude-opus-5-5` | 測定型 medium／判断型 high | 15〜30 分 |
| プレモーテム | `ti-<テーマ>-premortem` | ステップ5-4。一方通行の判断では必須 | ホストが推す理由・ボード・棄却案 | `--challenger` | `--challenger-model` | high（一方通行は xhigh） | 10 分 |
| リント | `ti-<テーマ>-lint` | ステップ6-2 | なし（ログ全体を読む） | claude | `claude-opus-5-5` | low | 5 分 |

- **測定型と判断型の見分け**：「走らせて数値を閾値と比べる」「grep して数える」なら測定型。「ログを読んで原因を追う」「kill 条件に該当するか解釈が要る」なら判断型
- **effort を上げすぎない理由**：高い effort のエージェントは作業範囲を広げがちで、kill テストで困るのは「H2 を壊しに行ったはずが H3 まで調べて帰ってくる」こと。測定型を medium に留めるのはブリーフの境界を守らせるため
- **トークンが厳しいときの段階的な切り下げ**：リントと分類を `claude-haiku-5-5` / low に、測定型 kill テストを `claude-sonnet-5-5` / medium に。判断を含む役割は最後まで Opus に残す
- fork（ホストの文脈を引き継ぐ Agent ツール）は使わない。ホストのモデル・effort・本命まで引き継ぐため、盲検が崩れ、出力単価も高い

## 起動手順

```bash
THEME=queue                           # ステップ0 で決めたテーマ名
ROLE=h2                               # facts / hypo / h<N> / premortem / lint
NAME="ti-$THEME-$ROLE"
KIND=claude                           # hypo / premortem は --challenger の値
MODEL=claude-opus-5-5                 # hypo / premortem は --challenger-model の値
EFFORT=medium                         # 役割表のとおり
AGENT_ARGS=""                         # --agent-args があればその内容。無ければ空

# 名前の衝突を避ける（生きているエージェントの中で一意）
if herdr agent list | jq -r '.result.agents[].name // empty' | grep -qx "$NAME"; then NAME="$NAME-2"; fi

OUT=$(herdr tab create --workspace "$HERDR_WORKSPACE_ID" --cwd "$PWD" --label "$NAME" --no-focus)
TAB=$(echo "$OUT"  | jq -r '.result.tab.tab_id')
PANE=$(echo "$OUT" | jq -r '.result.root_pane.pane_id')

case "$KIND" in
  claude) herdr agent start "$NAME" --kind claude --pane "$PANE" -- --model "$MODEL" --effort "$EFFORT" $AGENT_ARGS ;;
  codex)  herdr agent start "$NAME" --kind codex  --pane "$PANE" -- ${MODEL:+-m "$MODEL"} $AGENT_ARGS ;;
esac
```

- `--workspace "$HERDR_WORKSPACE_ID"` と `--no-focus` を省略しない。タブ内で分割しない
- `agent start` の応答で `.result.agent.agent_status` が `idle`、`interactive_ready: true` を確認する。`agent_not_ready` や `blocked` なら `herdr agent read "$NAME" --source visible` で画面を読み、ユーザーに見せて指示を仰ぐ。ログイン・承認のダイアログに勝手に答えない
- codex の effort は CLI の既定に任せる。ユーザーが指定した場合だけ `--agent-args` で渡す
- 起動に失敗して続行できない場合は、自分が作ったタブだけ `herdr tab close "$TAB"` で閉じてから報告する
- タブ名・TAB・PANE・役割・ラウンドをログの付録「サブエージェントの記録」に残す（再開時に同じタブへ続きを頼める）

## 送信と回収

```bash
PROMPT=$(cat <<'__PROMPT__'
<ブリーフ固定文（共通前文 + 役割本文）>
__PROMPT__
)

# 単発
herdr agent prompt "$NAME" "$PROMPT" --wait --timeout 1800000
herdr agent read "$NAME" --source recent-unwrapped --lines 300

# 並列（kill テスト）: 全員に送ってから 1 つずつ待つ
herdr agent prompt "ti-$THEME-h1" "$PROMPT1"
herdr agent prompt "ti-$THEME-h2" "$PROMPT2"
herdr agent wait "ti-$THEME-h1" --timeout 1800000
herdr agent wait "ti-$THEME-h2" --timeout 1800000
herdr agent read "ti-$THEME-h1" --source recent-unwrapped --lines 300
herdr agent read "ti-$THEME-h2" --source recent-unwrapped --lines 300
```

- 応答の状態で分岐する：`done` / `idle` → 回収、`blocked` → 画面を読んでユーザーに提示、`agent_prompt_stalled` → `herdr agent get` と `agent read` で確認、`timeout` → 進捗を報告して待つか中断するかを聞く
- `--lines` を増やしても返答の先頭が読めないときだけ、フォールバックとして scratchpad に書かせる：

```bash
herdr agent prompt "$NAME" "直前の回答の全文を Markdown で <scratchpad>/ti-$THEME/$NAME.md に書き出し、そのパスだけを返答してください。" --wait --timeout 120000
```

- 同じ仮説の再テストは同じタブに続けて送る。前回の結果との差分だけを頼めばよい

## ブリーフ固定文

サブエージェントは呼び出し元の会話を一切知らない。**共通前文 + 役割本文** で自己完結させる。`<...>` はホストが埋める。盲検の欄に書いたものは埋めない。

### 共通前文（全役割）

```
あなたは技術探究の「<役割名>」です。このタブの外の会話は知らない前提で、以下に書かれたことだけを根拠に作業してください。

制約:
- リポジトリのファイルを変更しない。コミットしない。実験用のファイルは <scratchpad>/ti-<テーマ>/<役割>/ 配下にだけ作る
- 推測を事実のように書かない。事実には根拠（file:line、実行したコマンドと出力、数値）を添える
- 確信度・パーセント・「おそらく正しい」「推奨」のような評価は書かない。観測と、指定された形式だけを返す
- 返答は最後にまとめて指定の形式で出す。途中経過の長い出力はそのまま貼らず、必要なら <scratchpad>/ti-<テーマ>/<役割>/ にファイルとして置いてパスを示す
- 判断に迷う承認（削除・push・外部送信）は実行せず、その旨を返答に書く
```

### 事実棚卸し（`ti-<テーマ>-facts`）

```
役割: 現状の事実の棚卸し（読み取り専用）
対象: <ディレクトリ・モジュール>
知りたいこと:
- <問い 1。「〜は今どう実装されているか」の形>
- <問い 2>

依頼:
- 対象のコードを読み、上の問いに事実として答えてください。仮説や改善案は不要です
- 事実ごとに根拠を file:line で示してください
- 読んでも分からなかったことは、分からなかったと書いてください

返答形式:
## 事実
| ID | 事実 | 根拠（file:line） |
| --- | --- | --- |
## 確認できなかったこと
- <項目>: <なぜ確認できなかったか>
```

### 盲検仮説生成（`ti-<テーマ>-hypo`）

```
役割: 仮説の独立生成
中核の問い: <1-1>
不変条件:
- <1-2 の一覧。出典付き>
現状の事実:
- <1-5 の一覧。F-ID と根拠付き>
観測事象（原因究明のとき）:
- <ログ・メトリクス・再現条件・発生時刻>

依頼:
- この問いに対する候補（方式 / 原因 / 実現条件）を 3〜5 個挙げてください。常識的な候補と、通常は検討されにくい候補（前提の 1 つを外した候補、現状維持、組み合わせ）の両方を含めてください
- 各候補について「正しければ何が観測されるはずか」「間違っていれば何が観測されるはずか」を 1 つずつ、指標・閾値・条件の形で書いてください
- 原因究明の場合は、各候補が上の観測事象のどれを説明でき、どれを説明できないかを表にしてください
- 必要なら <ディレクトリ> のコードを読んで構いません。読んだ場合は根拠を file:line で示してください
- 候補の優劣・おすすめ・確信度は書かないでください

返答形式:
## 候補
### 候補 1: <名前>
- 内容:
- 正しければ観測されるはずのこと（指標・閾値・条件）:
- 間違っていれば観測されるはずのこと（指標・閾値・条件）:
- 根拠（あれば file:line）:
（候補の数だけ繰り返す）
## 説明表（原因究明のみ）
| 観測 | 候補1 | 候補2 | ... |
| --- | --- | --- | --- |
（○ 説明できる / × できない / △ 条件付き。△ の条件を欄外に書く）
```

### kill テスト（`ti-<テーマ>-h<N>`）

```
役割: 仮説の反証テスト
仮説 H<N>: <仮説の文>
kill 条件: <指標・閾値・条件>
関係する不変条件（参考）:
- <関連するものだけ>
見るべき場所・使ってよい手段:
- <ファイル・ディレクトリ>
- <再現手順・コマンド・ベンチの方法・使ってよい環境>
作業場所: <scratchpad>/ti-<テーマ>/h<N>/ （ここ以外にファイルを作らない）

依頼:
- この仮説を壊す観測を得ることを目標に、kill 条件を実際に評価してください。「動くことを確かめる」のではなく「どの条件で kill 条件に該当するか」を調べてください
- kill 条件の評価に必要な最小限の作業に留め、他の仮説や周辺コードの改善には手を出さないでください
- 評価できない場合は、何が足りないか（権限・環境・データ・時間）を具体的に書いてください
- 直す・修正案を出すことは求めていません

返答形式:
## 仮説: H<N>
## kill 条件: <転記>
## 実施したこと
- <実行したコマンド・読んだファイル・作ったスクリプトのパス>
## 観測
| # | 観測 | 根拠（file:line / コマンドと出力 / 数値） |
| --- | --- | --- |
## kill 条件に該当: はい / いいえ / 判定不能
- 理由: <観測 # を引いて 1〜2 行。判定不能なら何が足りないか>
## 想定外の観測（あれば）
- <仮説と無関係に見つかった事実。評価や提案は書かない>
```

### プレモーテム（`ti-<テーマ>-premortem`）

```
役割: プレモーテム（事前検死）
前提: 次の案を採用して実装し、6 か月後に「失敗だった」と判断されたとします。
採用案:
<案の内容。何をどう変えるか。ホストが推す理由・比較表・棄却案は含めない>
不変条件:
- <1-2 の一覧>
現状の事実:
- <1-5 の一覧>

依頼:
- 失敗の最もありそうな理由を 3 つ、ありそうな順に挙げてください。技術的な理由だけでなく、運用・移行・組織の理由も候補に入れてください
- 各理由について、今の時点でそれを観測・検証できる方法を 1 つ、指標・閾値・条件の形で書いてください
- 案の良い点、採用の是非、代替案は書かないでください

返答形式:
## 失敗理由
### 1. <理由>
- なぜ起きるか:
- 今観測できる形（指標・閾値・条件）:
### 2. <理由>
...
### 3. <理由>
...
```

### リント（`ti-<テーマ>-lint`）

```
役割: 探究ログのリント（形式チェックのみ）
対象: <ログのパス>（読み取り専用。変更しない）

チェック項目:
1. 「3. 反証条件の事前登録」の登録日時が「4. 探究ループ」の最初のラウンドの日時より前か
2. 「確信度の更新」のすべての行に、根拠となる観測 ID（O-番号）が付いているか
3. すべての kill 条件に指標・閾値・条件の 3 要素があるか
4. ステータスが「棄却」の仮説すべてに、根拠となる観測 ID があるか
5. 「6. 決定記録」の「覆す条件」が、観測可能な形（指標・閾値・条件）で書かれているか
6. 「5-3 可逆性と閾値」で一方通行と分類された候補に、「5-4 プレモーテム」の結果が付いているか
7. 方式選定モードの場合、仮説ボードに「現状維持」が含まれているか。含まれていなければ、含められない理由が書かれているか
8. 仮説ボードの各仮説に「出自」が書かれているか

内容の良し悪し（仮説の妥当性、決定の是非）は判定しないでください。

返答形式:
| # | 項目 | 結果（✅ / ❌） | 該当箇所（❌ のとき） |
| --- | --- | --- | --- |
```

## ホスト側の受け取り規則

- 返答から **観測だけ** を取り出し、O-ID を振ってログに転記する。サブエージェントが確信度・推奨・修正案を書いてきても採用しない
- **決定を変えうる観測は、ホストが根拠（file:line・数値）を自分で開いて確認する。** 確認できなければ ⚠️ を付ける
- 「kill 条件に該当: はい／いいえ」はサブエージェントの判定であって確信度ではない。ホストは観測を見て自分で該当を判断し直す。食い違えばホストの判断を採り、理由を書く
- 「想定外の観測」は新仮説の候補。テストする前にステップ2〜3（kill 条件の事前登録）を通す
- 盲検仮説生成の候補にホストの候補と同じものがあっても、出自は「対抗役」と「ホスト」の両方を記録する（独立に同じ候補が出たこと自体が情報）
- 対抗役の返答が、渡していないはずのホストの本命を言い当てていても、それは独立の収束であって漏洩ではない。ただしブリーフに本命を書いてしまっていた場合は盲検が崩れたとしてログに記す

## タブの後始末

- 既定ではタブを閉じない。ユーザーが結果を眺めたり、同じ仮説の再テストを同じタブに頼めるように残す
- `--close` またはユーザーの指示があったときだけ、このスキルが作ったタブを `herdr tab close "$TAB"` で閉じる。他のタブ・ペイン・ワークスペースに触らない
- サブエージェントがリポジトリ内のファイルを変更していた場合は `git status --short` で確認し、ユーザーに報告する
