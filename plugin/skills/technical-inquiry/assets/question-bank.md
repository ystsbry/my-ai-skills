# 問いと手段のカタログ（technical-inquiry）

各ステップでホストが自分に（そしてユーザーに）投げる問いと、反証の手段をまとめる。全部を使う必要はない。該当する節だけを Read する。

## 不変条件を見つける問い（ステップ1-2）

「今こう作っているから」を外して、「本当に守らなければならないこと」だけに戻すための問い。

- この機能・変更が無かったとして、それでも最低限守られないと困ることは何か
- それを数値で言うと何か（件数・秒・金額・割合）。測れないなら、それは不変条件ではなく願望ではないか
- 誰が決めた条件か。どこに書いてあるか。出典が無いなら前提候補（1-3）へ
- 破ったら誰に何が起きるか。起きることが「困る」で済むなら不変条件ではない
- 今の実装の都合（ライブラリ・スキーマ・デプロイ手順）から来ている条件ではないか

典型的な不変条件の例：

| 領域 | 例 | 検証可能な形 |
| --- | --- | --- |
| データ | 予約が失われない／二重に確定しない | 障害注入後の件数一致、冪等性テスト |
| 時間 | X 秒以内に応答／Y 分以内に反映 | p95・p99 の閾値 |
| 整合 | 残高が負にならない／在庫と注文が一致する | 不変条件チェックのクエリが 0 件 |
| 互換 | 既存クライアントを壊さない | 旧クライアントの E2E が通る |
| コスト | 月額 Z 以下 | 見積りと実測 |
| 運用 | 一人で 30 分以内に復旧できる | 復旧手順のリハーサル |

## 前提を崩す問い（ステップ1-3）

- **誰の制約か。** 自分たちが決めたのか、他チームか、顧客か、過去の自分か
- **いつ決まったか。** そのときの理由は今も成り立つか
- **固定か可変か。** 変えるのに何が要るか（会話 1 回で変わるのか、契約変更なのか）
- **外したら最悪何が起きるか。** 起きることが許容範囲なら、それは制約ではなく好みではないか
- **現状維持のコストは何か。** 変えないことにもコストがある。それは数えられているか
- **「〜しかない」「必ず」「全部」** と書かれているものに反例は 1 つも無いか

よく見かける偽の制約の例：「DB は変えられない」「同期でなければならない」「このライブラリしか使えない」「リリースは月 1 回しかできない」「全件再計算が必要」。それぞれ「誰が・いつ・なぜ」を聞くと、過去の都合だったことが多い。

## 仮説を広げる問い（ステップ2）

対抗役に盲検で出させるのが基本だが、ホスト自身の候補を広げるときにも使う。

**原因究明**：

- すべての観測を説明する最小の原因は何か。説明できない観測が残る仮説はどれか
- いつから起きているか。その時刻の前後で何が変わったか（デプロイ、設定、データ量、外部の変更）
- 再現条件は何か。再現しない条件は何か。その差が原因の輪郭を描く
- 症状が出ている場所と原因がある場所は同じか（下流の症状、上流の原因）
- 複数の原因が重なっていないか。1 つ直しても残る症状は何か

**方式選定・実現可能性**：

- 現状維持案（何もしない）は候補に入っているか
- やらない案・スコープを削る案は候補に入っているか
- 2 つの案を条件で切り替える組み合わせは成り立つか
- 前提を 1 つ外したら出てくる案は何か（1-3 で可変にした前提を使う）
- 他のチーム・他のシステム・他の業界では同じ問題をどう解いているか

## kill 条件の書き方（ステップ3）

**3 要素**：指標（何を測るか）・閾値（いくつを超えたら／下回ったら）・条件（どういう状況で）。

| 悪い例 | なぜ悪いか | 良い例 |
| --- | --- | --- |
| SQS 化してうまくいかなければ不採用 | 何をもって「うまくいかない」か決まっていない | SQS 化しても、ピーク相当 500 req/s で p95 が 2 秒を超えるなら不採用 |
| ロック競合が原因かどうか確認する | 確認であって反証ではない | ロック競合が原因なら、ロック待ち合計が遅延の 50% 以上を占めるはず。20% 未満なら棄却 |
| ライブラリ X で Y ができるか試す | できたら採用、できなかったら？が無い | X で Y を試み、公式 API に該当機能が無く、回避策が 100 行を超えるか非公開 API に依存するなら不可 |
| 負荷をかけて様子を見る | 「様子」は観測ではない | 同時 1,000 接続を 10 分維持し、エラー率 0.1% 超または メモリが 2GB を超えたら不採用 |
| 現場に聞いてみる | 誰に何を聞くかが無い | 運用担当 2 名に復旧手順を実演してもらい、30 分を超えたら不採用 |

**書くときの問い**：

- この仮説が間違っていたら、何が観測されるはずか。それを測る最も安い方法は何か
- 結果がどちらに転んでも判断が同じなら、このテストは要らない。判断が変わる形に設計し直せるか
- 1 つのテストで 2 つの仮説を同時に判別できないか（原因究明では説明表の × の列）
- 「動くことを確かめる」になっていないか。「どの条件で動かなくなるか」に言い換える
- 閾値は不変条件（1-2）から導けているか。導けないなら閾値の出典を書く

## 判別テストの手段（コスト順）

| 手段 | 向いている仮説 | コスト | 注意 |
| --- | --- | --- | --- |
| ドキュメント・ソースの読解 | 実現可能性（API の有無）、方式の制約 | 分 | 「書いてある」と「動く」は別。重要なら 1 段下の手段で裏取り |
| 既存ログ・メトリクスの突合 | 原因究明（時刻の一致・不一致） | 分〜時間 | 相関と因果を分ける。一致しない事例を必ず探す |
| 再現スクリプト | 原因究明（再現条件の特定） | 時間 | scratchpad に置く。本番データを使うなら許可を取る |
| ミニ実装（scratchpad） | 実現可能性、方式の核心部分 | 時間〜半日 | 核心だけを作る。周辺を作り込まない |
| ベンチマーク | 性能に関する方式仮説 | 時間〜半日 | 本番相当の負荷・データ量でなければ閾値の意味が変わる。条件を記録する |
| 本番相当環境でのスパイク | 統合・運用に関する仮説 | 日 | 最後の手段。ここまで来る前に上の手段で候補を絞る |
| シナリオで動かす（design-story-telling） | 例外・障害・体験の整合性 | 時間 | 実測できない仮説の反証に使える。特に例外・障害系 |

## システム思考の問い（ステップ5-2）

- この変更で速くなる・楽になるのはどこか。その分、遅くなる・負荷が増えるのはどこか
- 上流は変更後の速度で供給できるか。下流は変更後の速度で受け取れるか（バックプレッシャー）
- フィードバックループはあるか。リトライが負荷を増やし、負荷がリトライを増やす構造になっていないか
- 効果が出るまでの遅延はどれくらいか。遅延があると人は「効いていない」と判断して余計な操作をしないか
- 詰まりが解消されたのか、別の場所に移っただけか
- 容量の上限はどこに移るか。次に詰まるのはどこか

## 可逆性の問い（ステップ5-3）

- 戻すのに何が要るか。設定・フラグで戻るか。コードの revert で戻るか。データ移行が要るか
- 外部との契約（API・ファイル形式・イベントのスキーマ・顧客との約束）を変えるか
- 併存期間は要るか。要るなら、その間の運用コストは
- 決定を遅らせられるか。遅らせた場合、いつが最終責任時点か。それまでに何が分かれば決められるか

可逆化の手段：

| 手段 | 使いどころ |
| --- | --- |
| フィーチャーフラグ | 新旧を切り替えられる形で入れる。切り戻しがフラグ 1 つになる |
| アダプタ層・抽象化 | 方式の違いをインターフェースの裏に閉じ込める。差し替え可能にする |
| 新旧併存（デュアルライト・シャドウ実行） | 新方式を本番で走らせつつ、旧方式を正とする期間を置く |
| 段階的な移行 | 一部のユーザー・テナント・経路だけ新方式にし、観測してから広げる |
| 決定の延期 | 最終責任時点まで両方の選択肢を生かす。延期のコストを明記する |

## 統合の問い（ステップ5-1）

- A と B が対立する根にある前提は何か。どの前提が成り立つと A が正しく、どう違うと B が正しいか
- A と B が守ろうとしている不変条件は同じか。違うなら、両方を満たす第三の形はあるか
- 「条件 C なら A、そうでなければ B」の形で切り分けられるか。C は実行時に判定できるか
- 中間案になっていないか。中間案は両方の弱点を持つことが多い。統合案は対立を解消しているか
- 統合案にも kill 条件を付けたか。統合案は新しい仮説であって、結論ではない

## プレモーテムの問い（ステップ5-4）

対抗役に投げるのが基本。ホストが自分で考えるときの補助。

- 半年後に「失敗だった」と言われたとして、最もありそうな理由は何か。技術以外（運用・移行・組織・コスト）も含めて
- その理由は、今の kill 条件のどれかで評価済みか。評価済みなら観測 ID は。未評価なら、今観測できる形は何か
- 成功したとしても「こうしておけばよかった」と言われるとしたら何か
- 一方通行の判断なら、未評価の失敗理由を残したまま決めてよい理由は何か（無ければ決めない）
