# 実例: 「生データの一覧」から「論点マップ」への再編（予約失敗エラーのスパイク）

論点抽出、特に**中核概念（共通言語）の探索**がうまくいった実例。あるスパイク調査
「全サービスタイプの予約失敗エラー洗い出しと、失敗理由の伝え方の方針決定」の
ドラフトが v1 → v2 でどう変わったかの記録。ステップ4（中核概念の探索）で参照する。

## Before（v1）: 実装側の分類軸で書かれた資料

v1 の章構成は、調査で得た**生データの分類**がそのまま骨格になっていた。

```
02_errors-realtime-on-demand.md   ← サービスタイプ別のエラー一覧
03_errors-bus-stop.md
04_errors-advance-reservation.md
05_support-api-errors.md
06_message-unification-matrix.md  ← サービスタイプ × カテゴリのマトリクス
...
```

内容は正確だったが、レビューで「マトリクスがわかりづらい」「どこを読めば意思決定
できるのかわからない」という指摘を受けた。**エラーコード別・API別という軸は、
調査した側の整理であって、意思決定する側の問いに沿っていなかった**。

## 転換点: 元の問いの生の言葉に立ち返る

PBI の背景にはこう書かれていた。

> ユーザーは「**時間を変えれば予約できるのか、もう無理なのか**」を判断できず、
> 代替手段の選択（時間変更か別の交通手段か）がしにくい。

ここから「これは文言の丁寧さの問題ではなく、**まず2択が示されていない問題**」と
捉え直し、次の2区分を最上位の軸に置いた。

| 区分 | 定義 | ユーザーが取る行動 |
| --- | --- | --- |
| **区分A: サービス内で完結する行動** | 条件（時間・場所・人数・決済手段）を変更すれば直ちに再試行できる | 時間変更／場所変更／人数調整／そのまま再試行 |
| **区分B: サービス外の行動** | ユーザーの条件変更では解消できない | 別の交通手段を検討／問い合わせ／復旧を待つ |

ポイントは3つ：

1. **軸の出どころがユーザーの生の言葉**（「時間を変えれば取れるのか、もう無理なのか」）
   であること。エラーコードやHTTPステータスといった実装側の語彙からは出てこない
2. **判別基準を操作的に定義した**こと：「バックエンドが『再試行すれば解消しうる』と
   判定できているか」。ロック競合(409)は明示的に再試行可能と判定しているのでA、
   想定外例外・外部API障害は解消時期が不明なのでB、と機械的に判定できる
3. **第3状態「⚠️A/B判別不能」を許した**こと。「手配可能な車両がありませんでした」は
   時間を変えれば取れるのか全滅なのか不明＝AでもBでもない。この判別不能の存在自体が
   「本PBIの実質的なゴールは判別不能を減らすこと」という資料全体の主張になった

## After（v2）: 5論点マップが骨格、生データは付録

v2 では論点マップが資料の骨格になり、エラーの生一覧は根拠として付録に降りた。

```
PBIの問い: 予約に失敗したユーザーが「サービス内でやり直せる(A)」か「別の手段を
           探すべき(B)」かを判断でき、A ならば変更すべき条件が分かる状態にするには？
│
├─ 論点1【事実確認】A/Bの情報はどこで失われているか ──── ✅ 調査で確定
│   ├─ 1-1 BE: コードの段階で失われる（汎用コードに A と B が同居）
│   └─ 1-2 FE: 表示の段階で捨てる（特定条件のときだけ文言が生きる）
├─ 論点2【Dev方針】どう直すか ────────────── 推奨提示済み・Dev共有待ち
│   ├─ 2-1 BE: A/Bが判る粒度への原因分離
│   └─ 2-2 FE: 安全な取り込み（ステータス別の表示可否ルール）
├─ 論点3【PO決定】何をどう伝えるか ──────────── 材料提示済み・決定待ち
├─ 論点4【トレードオフ】一長一短があり「是正」と断定できないもの
└─ 論点5【実行計画】どう進めるか
```

章構成もこの5論点＋付録に組み替わった（issue1〜issue5 の章＋appendix）。

## この実例から抽出できる教訓

- **調査の分類軸と意思決定の分類軸は別物**。生データの整理をそのまま資料の骨格に
  すると「正確だが判断できない」資料になる
- 中核概念の探索は「元の問いの生の言葉に含まれる選択の構造」を探すのが近道
- 軸には**操作的な判別基準**と**第3状態**をセットで付けると、こじつけを防げて、
  判別できない領域そのものが論点として浮かび上がる
- 「事実 → Dev方針 → PO決定 → トレードオフ → 実行計画」の型で並べると、各論点の
  ステータス（確定済み／共有待ち／決定待ち）がそのまま資料の進捗表示になる
- v1 を書いてから気づくと章構成の全面組み替えになる。**執筆前に論点抽出をやる**のが
  このスキルの存在理由
