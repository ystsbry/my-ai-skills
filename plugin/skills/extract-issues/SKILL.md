# 論点抽出スキル（extract-issues）

任意の素材から**論点**（決めないと先に進めない問い・対立や一長一短のある選択）を抽出し、型・決定者・ステータス・依存関係を付けて「論点一覧＋論点マップ」に構造化します。

このスキルの中心的な価値は、単なる箇条書きの列挙ではなく：

1. **論点とそれ以外（事実・確定済み制約・作業タスク）を分離する**こと
2. 論点群を貫く**中核概念（共通言語）**を発見し、資料全体の骨格にすること
3. 論点ごとに**誰が・何を材料に決めるのか**を明らかにすること

## 入力

```
# Claude Code（ybaba プラグイン経由）
/ybaba:extract-issues <素材（ファイルパス・ディレクトリ・本文貼り付け）>

# OpenAI Codex CLI
$ybaba:extract-issues <素材>    # marketplace 経由のプラグイン
$extract-issues <素材>          # ~/.agents/skills/ fallback 導入時
```

素材の例：スパイクPBI（README.md）、調査メモ、ドラフト一式（`draft/vN/`）、design-doc、会議メモ・会話ログ、口頭説明。複数を組み合わせてもよい。

## 3つのモード

| モード | 使う場面 | やること |
| --- | --- | --- |
| **順抽出** | 調査・執筆の**前**。PBIや生の調査メモから論点を洗い出したい | 素材から論点を抽出・構造化する |
| **逆抽出** | 既成のドラフト・資料が**すでにある**。レビューや読解の前に論点を把握したい | 資料が「何を論点とし、どの章で、何を根拠に、どう結論しているか」を逆算して一覧化する |
| **突き合わせ** | ドラフトのレビュー。論点の**漏れ・すり替え**を検出したい | 逆抽出＋（PBI等から）独立に順抽出し、両者の diff を取る |

素材の種類からモードを推定し、**着手前にユーザーに確認**する（「ドラフトがあるので逆抽出モードで進めます。レビュー目的なら突き合わせまでやります」など）。

---

## ステップ1: 入力とモードを確認する

1. 素材をすべて読む。ディレクトリを渡された場合は配下の文書を一通り読む
2. **元の問いを特定する**。PBIの背景・概要にある「ユーザー/依頼者の生の言葉」を見つけて引用できるようにしておく（ステップ4で使う）
3. モードと、出力の用途（調査設計・レビュー準備・整理）を確認する

## ステップ2: 論点候補を洗い出す

素材を走査し、以下に当てはまる箇所を論点候補として拾う。この段階では絞り込まず、広めに拾う。

**論点候補の基準**（「〜すべきか」「〜でよいか」「〜はどうなっているか」の形の問いに直せるもの）：

- 決めないと先に進めないこと（意思決定が必要）
- 選択肢が複数あり、対立・一長一短があること
- 事実なのか判断なのか曖昧なまま書かれていること
- ステークホルダー間（PO/Dev/運用など）で認識が割れうること
- チケット・PBIが**名指しした問いや調査起点**（明示リストがある場合は消化状況を必ず追跡する）
- 「要確認」「TBD」「暫定」と書かれたまま放置されている箇所

**論点ではないもの**（拾ったら「除外リスト」へ回し、理由を添える）：

- 単なる事実（確認すれば終わり、選択の余地がない）→ ただし「未確認の事実」は**事実確認型の論点**になる
- 確定済みの制約（例: 「二重決済防止のため汎用文言を維持する」と既に決まっている）→ 前提として扱う
- 作業タスク（決定ではなく実行の話）→ 実行計画型の論点の下位項目か、スコープ外

## ステップ3: 型分類と属性付け

各論点候補を5つの型に仕分ける。

| 型 | 定義 | 見分け方（問いの形） |
| --- | --- | --- |
| **事実確認** | 現状がどうなっているかがまだ確定していない | 「実際は〜なのか？」「どこで〜が起きているか？」 |
| **Dev方針** | 実現手段・技術方針をチームが決める | 「どう直すか」「どの方式にするか」 |
| **PO決定** | 価値・体験・優先度を意思決定者が決める | 「何をどこまでやるか」「どう伝えるか」「どれを優先するか」 |
| **トレードオフ** | 一長一短があり「是正」と断定できない。比較を提示して判断を仰ぐ | 「AとBどちらを取るか（どちらにも代償がある）」 |
| **実行計画** | 決定後の進め方・分割・順序 | 「どこから着手するか」「どう分割するか」 |

各論点に以下の属性を付ける：

- **決定者**: PO / Dev / 両方（プロジェクトに合わせて「意思決定者/実装チーム」等に読み替えてよい）
- **ステータス**: `未着手` → `調査中` → `材料揃い（決定待ち）` → `決定済み`
- **依存関係**: 原則として「事実確認 → Dev方針・トレードオフ → PO決定 → 実行計画」の順に依存する。事実が未確定のままの方針論点には ⚠️ を付けて明示する

型が2つにまたがる場合は分割する（例: 「500を400にすべきか」は、Dev方針（技術的に安全か）とPO決定（スコープに含めるか）に割れることが多い）。

## ステップ4: 中核概念（共通言語）を探索する

論点が多い（目安5個以上）とき、バラバラの論点を貫く**上位の軸**を探す。これが見つかると、資料全体が「生データの分類」から「意思決定の地図」に変わる。実例は `assets/good-example.md` を Read して参照すること（エラー一覧の羅列が「区分A/B」という軸の発見で5論点マップに再編された事例）。

**探索のヒューリスティクス**：

1. **元の問いの生の言葉に立ち返る**。実装・データ側の分類軸（エラーコード別、API別、画面別…）ではなく、ステップ1で特定した「ユーザー/意思決定者の生の言葉」に含まれる**二択・選択の構造**を探す（例:「時間を変えれば取れるのか、もう無理なのか」→ 対処可能/不能の2区分）
2. **候補を複数出して比較する**。各候補について「全論点候補を貫けるか」「例外が少ないか」「意思決定者がその軸で語れるか」を比べる
3. **判別基準を操作的に定義する**。「AとBを分ける基準は何か」を、コードや事実で判定可能な形で書く（例:「システムが『再試行すれば解消しうる』と判定できているか」）
4. **第3状態を許す**。きれいに二分できない現実は「⚠️判別不能」のような第3状態として明示する。判別不能の存在自体が重要な論点になることが多い
5. **無理に作らない**。論点が少ない・軸が見つからない場合は、中核概念なしの素直な一覧でよい。こじつけの軸は資料を歪める

## ステップ5: 事実と判断を分離する（リンティング）

出力前に、各論点の記述を以下の基準で点検する：

- **事実には根拠を付す**（コードなら `file:line`、資料なら文書名と該当箇所）
- **未確認・伝聞には ⚠️ を付す**。根拠のない断定を書かない
- 「〜と断定できない」ものを事実のように書いていないか（該当したらトレードオフ型か事実確認型に回す）
- 選択肢に**現状維持**が含まれているか（現状維持できない理由があるなら、それも判断材料として書く）

## ステップ6: 出力する

`assets/issues-template.md` を Read で読み込み、そのフォーマットに従って以下を**コンソールに全文出力**する：

1. **中核の問い**（1文）
2. **中核概念（共通言語）**（見つかった場合のみ）
3. **論点マップ**（型ラベル・ステータス付きのツリー）
4. **論点一覧表**（ID・型・問い・決定者・ステータス・依存・材料）
5. **各論点の詳細**（問い／なぜ論点か／選択肢／判断材料）
6. **論点から除外したもの**（＋理由）

ファイルには保存しない。**ユーザーが保存先を指定した場合のみ**（例: `pbi/642/issues.md`）そのパスに保存する。

### 逆抽出・突き合わせモードの追加出力

**逆抽出**では、上記に加えて**章→論点トレーサビリティ表**を出す：

| 資料の章 | 扱っている論点 | 資料の結論 | 根拠の有無 |
| --- | --- | --- | --- |

**突き合わせ**では、さらにPBI・チケットから**独立に順抽出した論点**（ドラフトを読む前に導出するのが理想。読んでしまった場合はPBIの記述だけを根拠に再導出する）とドラフト側の論点の diff を取り、以下の3分類で報告する：

- **漏れ**: PBIが求めているのにドラフトが論点として立てていないもの（チケットが名指しした調査起点の未消化を含む）
- **すり替え**: ドラフトが立てた論点が、元の問いと微妙にズレているもの（例: 「どう伝えるか」を問われているのに「どう実装するか」だけ答えている）
- **非論点**: 論点として立っているが、実は確定済みの制約や単なる事実であるもの

## ステップ7: すり合わせと更新

出力後、ユーザーのフィードバックで以下を調整する：

- 論点の過不足（「これは論点ではない」「これが抜けている」）
- 型・決定者の割り当て修正
- 中核概念の妥当性（別の軸のほうがよいか）
- ステータスの更新（このスキルの出力は生きたドキュメントとして、調査・決定の進行に合わせて更新してよい）

---

## 注意点

- **論点の言葉は意思決定者の言葉で書く**。実装用語だけの論点（「RSH50001を分離すべきか」）は、意思決定者が判断できる形（「定員超過と対象外エリアを同じ『システムエラー』のまま出し続けてよいか」）に翻訳する
- **結論を出さない**。このスキルの成果物は判断材料の地図であり、決定はユーザー・PO・Devが行う。推奨を書く場合は「推奨」と明示し、根拠を添える
- 素材が巨大な場合（ドラフト10章超など）は、章ごとに候補抽出→統合の順で進め、読み飛ばした部分があれば必ず申告する
- 突き合わせモードの diff は指摘リストではなくレビューの**入力**。断定的な非難調ではなく、レビュアーが検証すべき箇所の候補として提示する
