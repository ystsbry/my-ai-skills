# SVG ビルダー（svg-builder）

説明文から、妥当で自己完結した SVG を 1 つ作る。

ここでの失敗は「見た目が悪い」ことではなく、**重なり**である。文字が箱からはみ出す、矢印が無関係なノードを横切る、viewBox が短すぎて内容が見切れる。座標をトークンごとに思いつきで決め、キャンバス全体を見渡さないから起きる。以下のステップはすべてそれを防ぐためにあり、順番に意味がある。**計算が先、マークアップが次、動きが三番目、バリデータが四番目。**

## 入力

```
# Claude Code（ybaba プラグイン経由）
/ybaba:svg-builder <描きたいものの説明>

# OpenAI Codex CLI
$ybaba:svg-builder <描きたいものの説明>    # marketplace 経由のプラグイン
$svg-builder <描きたいものの説明>          # ~/.agents/skills/ fallback 導入時
```

既存の SVG（またはそれを含む HTML）のパスを渡せば、修正・デバッグの対象として扱う。本文中の `references/`・`assets/`・`scripts/` のパスはすべてこのスキルのディレクトリ基準で書いてある（Claude Code ではスキル読み込み時に示される Base directory を前置する）。

## ワークフロー

1. **要件の確認** — 下記 5 項目を埋める。質問は最大 2 つ。
2. **形式の振り分け** — ユーザーの名詞ではなく動詞から形式を選ぶ。
3. **台帳** — 座標の表をプレーンテキストで書く。省略しない。
4. **組み立て** — 台帳どおりにマークアップを出す。
5. **動き** — 図の振る舞いにふさわしい動きを付ける。任意ではない。
6. **検証** — `scripts/check_svg.py` を実行する。報告されたものを直して再実行する。

## 1. 要件の確認

| 項目 | 問い | 未指定時の既定 |
|---|---|---|
| 主題 | どんな実体があり、どう関係するか | — 必ず指定が要る |
| 意図 | 参照用、直感をつかむ、データ、装飾のどれか | 動詞から推測する（§2） |
| 媒体 | 再生コントロールが要るか | アニメーション（§5）。インタラクティブは依頼があったときだけ |
| 表示面 | 目標の幅は。ライト、ダーク、両方のどれか | 680px、両モード |
| 制約 | ブランドのパレット、フォント、JS 禁止、サイズ上限 | なし |

入力から答えが読み取れるところは黙って推測する。質問するのは、外すと描画全体が無駄になる場合だけ。主題が曖昧なら該当するが、幅が未指定なのは該当しない。

**入力が予算超過のとき:** 1 つの図に実体が 6 つ以上あると、箱の重なりや文字を横切る矢印が必ず起きる。疎な全体図と、サブフローごとの詳細 SVG に分割し、そうしていることをユーザーに伝える。正しい図が複数あるほうが、混み合った図 1 つより良い。

## 2. 名詞ではなく動詞で振り分ける

同じ主題でも、何を聞かれたかで欲しい絵は変わる。「Transformer のアーキテクチャ」ならラベル付きの箱が欲しいし、「attention はどう動くのか」なら重みで太さの変わる線の扇が欲しい。ここを外すと、技術的には妥当でも誰も聞いていない問いに答える図になる。

| 入力の形 | 形式 | 描くもの |
|---|---|---|
| 「順を追って説明して」「手順は」「流れは」 | フローチャート | 箱、一方向の矢印、分岐 |
| 「アーキテクチャは」「中身は」「X はどこにある」 | 構造図 | 入れ子のコンテナ、領域、包含関係 |
| 「X は*実際には*どう動く」「直感がほしい」「X がわからない」 | 説明図 | 仕組みそのもの、またはその空間的な比喩 |
| 「比較して」「どのくらい」「推移」「内訳」 | チャート | 軸、マーク、変数ごとに 1 つのエンコーディング |
| 「スキーマを見せて」「ER 図」 | **SVG にしない** | mermaid の `erDiagram` を出す。手置きのテーブル行は必ず破綻する |
| 「動かして」「アニメーションにして」「シミュレーションして」 | その形式本来の動きを強める | 動きはすでに付いている（§5）。より多くを担わせる依頼 |

限定のない「X はどう動く」には説明図が既定で、より野心的な選択でもある。箱のほうが安全に思えてもフローチャートに逃げない。抽象的な主題には幾何を発明する。ハッシュテーブルは漏斗がアイテムをバケツにばらまく絵、コールスタックは文字どおり積み上がったフレーム、attention は 1 つのトークンから他の全トークンへ重み付きの線が扇状に伸びる絵。**良い説明図は、ラベルをすべて消しても読める。** そうなっていないなら、レイアウトがまだ意味を担えていない。

1 つの SVG に複数の形式を混ぜない。両方必要なら、間に文章を挟んで 2 つ出す。

選んだ形式の組み立てパターンは `references/forms.md` を読む。

## 3. レイアウト台帳

マークアップより先にこれを書き出す。ドキュメントではなく、出力を正しくするための工程である。思いつきの座標を、検算できる計算に変えるからだ。

```
CANVAS   幅 680、高さ 未定、セーフエリア x:40..640
TIER 1   y 40..84    箱 3 個 w=120  x=100,280,460   間隔 60,60     ✓ 3·120+2·60=480 ≤ 600
TIER 2   y 132..176  箱 1 個 w=180  x=250           中心 340       ✓
EDGES    (160,84)->(340,132) バス y=108 経由    横切るもの: なし   ✓
         (340,176)->(340,214)                  横切るもの: なし   ✓
MAX_Y    564（consumer の箱の下端）   ->   viewBox の高さ = 584
```

次に、この順で検算する。

1. **行が収まるか:** `n·width + (n−1)·gap ≤ 600`。幅 160px の箱 4 個を間隔 20px で並べると 700 で、収まらない。縮める、2 行目に折り返す、箱を減らす。
2. **横の間隔は 20px 以上**（同じ行の箱どうし）、**縦の間隔は 40px 以上**（段どうし）。矢印が見える余地を残す。
3. **すべてのエッジを、配置済みのすべての rect と突き合わせる。** 線が rect を横切るなら、L 字の折れ線 `M x1 y1 L x1 ymid L x2 ymid L x2 y2` で迂回する。突っ切らせない。
4. **viewBox の高さ = max_y + 20**。max_y は最も低い `y+height`、または最も低いテキストのベースラインにディセンダ分の 4px を足したもの。推測しない。余白も残さない。
5. **負の座標を使わない。** viewBox は 0,0 から始める。
6. **内容が狭くても viewBox の幅は 680 のまま**にし、内容を中央に寄せる。`width="100%"` ではブラウザが座標空間全体を拡大するので、幅 476 の viewBox では 14px の文字が黙って 20px で描画される。

文字幅の表、段の詰め方、衝突の迂回、ツリーのレイアウトなど詳しい計算は `references/layout.md` にある。段が 2 つ以上あるものを配置する前に読む。

## 4. 組み立て

`assets/scaffold.svg` から始める。アクセシビリティのブロックと矢印マーカーがすでに正しく入っている。

**最も多くの出力を壊す 5 つのルール:**

- **すべてのコネクタの path に `fill="none"`。** SVG の既定の fill は黒なので、これのない曲線コネクタは大きな黒い塊として描画される。生成 SVG で最も多いバグ。
- **箱の中のラベルはすべて `dominant-baseline="central"`**、`y` はそのラベルの行の中心に置く。箱全体の中心ではない。これがないと SVG は `y` をベースラインとして扱い、文字が約 4px 浮いてディセンダが下の行に食い込む。
- **`<text>` は折り返さない。** 改行はすべて明示的な `<tspan x="..." dy="1.2em">`。折り返しが要るラベルは長すぎるので、削る。
- **すべての `<text>` に明示的な fill か class を付ける。** 無指定だと黒を継承し、ダークモードで消える。
- **線は部品の縁で止める。** 止める座標は相手の位置とサイズから計算する。突き抜けさせて塗りの下に隠すのは、制御できない背景色に賭ける行為なので禁止。

**仕上げの既定値:** 枠線とエッジの stroke は `0.5px`（1px は重く見える）。角は控えめなら `rx="4"`、強調なら `rx="8"`、`rx ≥ height/2` はピル型を意図したときだけ。フォントサイズは 2 種類だけ（ラベル 14px、サブタイトル 12px、11px 未満は使わない）。ウェイトも 2 種類だけ（400、500）。英語ラベルは文頭だけ大文字。回転した文字、絵文字、手描き風アイコンのパスは使わない。

**グラデーション、影、ぼかし、発光は使わない。** 説明図で、本当に連続した物理量（温度の成層、圧力の低下、濃度）を表すときに限り、1 つのランプの 2 ストップ間の `<linearGradient>` を 1 つだけ許す。平坦な rect 2 つで同じことが言えるなら、rect 2 つにする。

**循環はリングとして描かない。** ここにある間隔の計算はすべて直交座標系で、円の周りを回る箱の衝突判定はない。周辺の箱が、自分が入力する先のステージに乗ってしまう。ステージは直線に並べ、戻りのパスか `↻` の記号でループを示す。ステージごとに詳細があるなら、代わりにステッパーを作る。

色とダークモードには固有の失敗パターンがある。fill を 1 つでも選ぶ前に `references/color.md` を読む。

## 5. 動き

**すべての図は動く状態で納品する。** 描く価値のある主題の多くは何かを*する*。データが流れる、状態が変わる、リクエストが伝わる。静止画では読み手が矢印の先からそれを再構成することになる。動きはそれを直接手渡す。

これが生む危険は装飾なので、基準は狭い。**動きは、図がすでに主張していることをエンコードしなければならない。** 理由もなく脈動する箱は、動きがないより悪い。存在しない振る舞いをほのめかすからだ。効果を発明せず、形式ごとの語彙から選ぶ。

| 形式 | 動くもの | 読み手が得るもの |
|---|---|---|
| フローチャート | エッジに沿って破線が進む。依存順にずらす | 方向と、何が何を待つか |
| 構造図 | 段階的な表示。コンテナが先、中身が後 | 包含関係。何の中に何があるか |
| 説明図 | 仕組みそのもの | 説明したい振る舞い |
| チャート | マークがエンコーディング軸に沿って伸びる | どの軸が値を担うか |

主題に本当に振る舞いがないとき（分類体系、凡例、固定された 2 つのものの比較）は、読む順に**段階的に表示する**のが誠実な動きである。それでも、部品がどの順で意味をなすかという本物の情報を教える。一度だけ再生して止まる。ループするのは連続した振る舞いだけで、ループは約 2 秒以内に収める。

**静止状態こそが図である。** スクリーンショット、PDF 書き出し、`<img src="…">`、動きの抑制設定を使う読み手は、1 フレームも再生されない状態でマークアップどおりのものを受け取る。だから要素自身の属性が*完成*状態を持ち、アニメーションは開始状態*から*走る。

```css
@keyframes reveal { from { opacity: 0; } to { opacity: 1; } }
@media (prefers-reduced-motion: no-preference) {
  .node { animation: reveal .4s ease-out both; }   /* 隠す指定はキーフレームの中に置く */
}
```

両端を書く。`from` だけのキーフレームは終端の値を要素自身のスタイルから取るので、`.node { opacity: 0 }` というルールと組み合わせると 0 から 0 へのアニメーションになり、要素は永遠に現れない。アニメーション自体は走るので、静かに、しかし完全に失敗する（`REVEAL_STUCK`）。マークアップに `opacity="0"` を書く、あるいは同じルールをガードの外に書くのがもう一方の失敗で、再生を見ない全員に白紙の絵を渡す（`STATIC_BLANK`）。どちらも「既定で動く」が持ち込む失敗パターンで、バリデータはそれぞれをエラーにする。

**唯一の例外は明示的な制約**であり、黙った判断ではない。ユーザーが静止を求めた、または対象が動かせない（印刷、静的だと告げられたレンダラ）場合。そのときは静止で作り、どのルールをなぜ外したかを（出力の約束どおり）述べ、`--allow-static` で検証する。「この主題は静的に感じた」はその例外ではなく、上の段階的な表示のケースである。

アニメーションを書く前に `references/animation.md` を読む。仕組みの選択（CSS、SMIL、JS）、形式ごとのレシピ、それぞれの罠がある。

## 6. 検証

```bash
python3 scripts/check_svg.py path/to/diagram.svg
```

出力したマークアップを解析し、次を報告する: `fill="none"` のないコネクタの path、コンテナからはみ出すと推定される文字、class のない `<text>`、viewBox で見切れる内容や余白に浮く内容、部分的に重なる rect、負の座標、11px 未満の文字、アクセシビリティのブロックの欠落。

§5 も強制する。アニメーションがまったくないのはエラーで、再生できないアニメーションもエラー（誰も定義していないキーフレーム、どの要素も持たない class、白紙の静止状態、`prefers-reduced-motion` のガードの欠落）。

報告されたものを直して、もう一度実行する。`--json` で機械可読な出力、`--strict` で警告でも非ゼロ終了、`--allow-static` で動きの検査を外す。最後のものは他人から渡された SVG をデバッグするためのもので、自分の出力で §5 を飛ばすためのものではない。HTML ファイルも受け付け、中の `<svg>` を取り出す。

警告は判定ではなく問いとして扱う。文字幅は文字数から推定しているので、広い箱の短いラベルへの警告は見る価値はあるが問題ないことも多い。*エラー*は交渉の余地がない。

## 出力の約束

- **1 回の返答に `<svg>` は 1 つ。** 壊れた試作を修正版の上に残さない。丸ごと置き換える。
- **自己完結。** 外部取得なし、ビルド工程なし、フレームワークなし。CSS はインライン。ライブラリはユーザーが求めたときだけ。
- **文章は SVG の外に置く。** タイトル、キャプション、説明の段落をマークアップに入れない。説明はメッセージで、描画はファイルで。
- **単純化したものを名指しする。** 図が実在するものを落としたとき（システム図のレプリケーション、フローのエラー分岐、ライフサイクルの失敗経路）、1 行で言う。難しい部分を黙って省いた図は間違ったモデルを教え、読み手にはそれが起きたと知るすべがない。
- ここにあるルールから外れるときは、どのルールをなぜ外したか 1 行で言う。

## 最終チェック

すべての行が真になるまでファイルを渡さない。* 付きはバリデータが検査する。

```
[ ] 台帳を書いた。各行の合計幅 ≤ 600
[ ] すべてのエッジをすべての rect と突き合わせた。意図しない交差ゼロ   *
[ ] すべてのラベル: 文字数 × 8 + 24 ≤ 箱の幅（日本語は 1 文字 × 15）    *
[ ] 箱の中のすべてのラベルに dominant-baseline="central"               *
[ ] viewBox の高さ = 最下端の要素 + 20。見切れなし                       *
[ ] すべてのコネクタ <path> に fill="none"                             *
[ ] すべての <text> に明示的な fill か class                           *
[ ] ほぼ黒の背景でも読める
[ ] 色だけで担っている区別がない
[ ] role="img" + <title> + <desc> が最初の子要素                       *
[ ] 動きがあり、図がすでに言っていることをエンコードしている             *
[ ] 動きは @media (prefers-reduced-motion: no-pref…) の中で宣言        *
[ ] 静止状態が完成した図。静止時に隠れているものがない                   *
[ ] <svg> はちょうど 1 つ。孤立した途中の試作がない
```
