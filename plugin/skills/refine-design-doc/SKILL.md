# Design Document 壁打ちスキル（refine-design-doc）

design-doc スキルで生成した Design Document を、**別プロセスのエージェントをレビュアー役にして壁打ち**し、改訂していきます。自分（ホスト）は執筆者兼ファシリテータ、サブエージェントは「初見のレビュアー」、ユーザーは「意思決定者」という役割分担です。

サブエージェントは Herdr の同じワークスペースに新しいタブを 1 つ作って起動します（herdr-subagent スキルと同じ方式）。壁打ちが終わっても**タブは閉じずに残し**、ユーザーが続きを頼んだり経過を見返せるようにします。

## 入力

```
# Claude Code（ybaba プラグイン経由）
/ybaba:refine-design-doc <Design Document のパス> [--kind claude|codex] [--model <モデル>] [--rounds N] [--focus <観点>]

# OpenAI Codex CLI
$ybaba:refine-design-doc <パス> [...]    # marketplace 経由のプラグイン
$refine-design-doc <パス> [...]          # ~/.agents/skills/ fallback 導入時
```

| オプション | 既定値 | 意味 |
| --- | --- | --- |
| `<パス>` | 必須 | design-doc スキルで保存した Markdown のパス。渡されなければユーザーに聞く |
| `--kind` | 自分と**別の**種類 | 壁打ち相手のエージェント種別。`claude` または `codex`。Claude Code から呼ばれたら既定は `codex`、Codex から呼ばれたら既定は `claude`（視点を変えるため）。同じ種類を指定してもよい |
| `--model` | エージェントの既定 | 壁打ち相手のモデル。claude / codex どちらも `--model <名前>` として起動引数に渡す |
| `--rounds` | 3 | 壁打ちの最大ラウンド数。収束すれば早く終わる |
| `--focus` | なし | 特に叩いてほしい観点（例: `移行手順`、`代替案`、`パフォーマンス`）。指定があれば毎ラウンドの指示に含める |

「codex の gpt-5 で」「claude の opus で」のようにプロンプト中で自然に指定されていれば、それを `--kind` / `--model` として扱う。

## 全体の流れ

1. 前提を確認し、対象ドキュメントと壁打ち相手を決める
2. 別タブにサブエージェント（レビュアー役）を立てる
3. ラウンドを繰り返す: レビュー依頼 → 指摘の整理 → ユーザー判断 → 改訂 → 再レビュー
4. 収束したら最終版を保存し、TL;DR で報告する。タブは残す

---

## ステップ1: 前提と入力を確認する

```bash
test "${HERDR_ENV:-}" = 1 && echo "in herdr: workspace=$HERDR_WORKSPACE_ID"
herdr agent start --help | grep -q -- '--kind' && echo "herdr 0.8+"
```

- `HERDR_ENV` が `1` でなければ Herdr の外で動いている。「Herdr のペイン内から実行してください」と伝えて中断する
- **ドキュメントのパスが渡されていなければユーザーに聞く。** 推測で探さない
- ドキュメントを読み、Scope / Background / ProblemStatement / Proposal の 4 セクションが揃っているか確認する。揃っていなければ design-doc スキルで先に作る、または不足を補うかをユーザーに確認する
- `--kind` / `--model` が指定されていなければ既定値を使い、**何と壁打ちするかを開始前に 1 行で伝える**（例: 「codex（gpt-5）をレビュアーにして最大 3 ラウンド壁打ちします」）。ユーザーが別のものを望むならここで変えられる
- `--model` に指定された名前が妥当かはスキル側で検証できない。起動に失敗したらエラー内容を見せて再指定を求める

### サブエージェント名

`review-<ドキュメント名のケバブケース>` を基本にする（例: `review-session-auth`）。`[a-z][a-z0-9_-]{0,31}` に収め、`herdr agent list` で生きているエージェント名と衝突しないようにする。

## ステップ2: 別タブにレビュアー役を立てる

herdr-subagent スキルの手順に従う。要点は以下のとおり。

```bash
NAME=review-session-auth
KIND=codex                       # または claude
MODEL=gpt-5                      # 指定が無ければ空

OUT=$(herdr tab create --workspace "$HERDR_WORKSPACE_ID" --cwd "$PWD" --label "$NAME" --no-focus)
TAB=$(echo "$OUT"  | jq -r '.result.tab.tab_id')
PANE=$(echo "$OUT" | jq -r '.result.root_pane.pane_id')

if [ -n "$MODEL" ]; then
  herdr agent start "$NAME" --kind "$KIND" --pane "$PANE" -- --model "$MODEL"
else
  herdr agent start "$NAME" --kind "$KIND" --pane "$PANE"
fi
```

- `--workspace "$HERDR_WORKSPACE_ID"` を必ず付ける（フォーカス中の別 space に作らないため）
- `--no-focus` でユーザーのフォーカスを動かさない
- タブ内で分割しない。1 タブ 1 エージェント
- `agent start` は対話可能になってから返る。`agent_not_ready` や `blocked` で返ったら `herdr agent read "$NAME" --source visible` で画面を読み、内容をユーザーに見せて指示を仰ぐ。**ログインや承認のダイアログに勝手に答えない**
- 起動に失敗して続行できない場合は、自分が作ったタブだけ `herdr tab close "$TAB"` で閉じてから報告する

---

## ステップ3: 壁打ちラウンドを回す

1 ラウンドは「レビュー依頼 → 指摘の整理 → ユーザー判断 → 改訂 → 再レビュー」。最大 `--rounds` 回。

### 3-1. レビューを依頼する

サブエージェントは呼び出し元の会話を知らない。**ドキュメントはパスで渡し、サブエージェント自身に読ませる**（同じ cwd で動いているので読める）。必要ならコードベースも調べさせる。

初回のプロンプト例：

```
あなたは設計レビュアーです。次の Design Document を読み、厳しめにレビューしてください。
対象: <パス>

前提:
- ファイルは変更しないでください。レビュー結果は返答としてのみ出してください
- 必要なら同じディレクトリ配下のコードを読んで、Background や Proposal の記述が実装と合っているか確認してください
<--focus があれば: - 特に「<観点>」について重点的に見てください>

以下の形式で返してください:
## 重大な懸念（このままでは進められないもの）
- <懸念>: <理由>。<どう直すべきかの案>
## 質問（判断が必要で、ドキュメントに答えが無いもの）
- <質問>
## 改善提案（あると良くなるもの）
- <提案>
## 良い点
- <点>

各項目は最大 5 つまで。優先度の高い順に並べてください。
```

2 ラウンド目以降は、前回の指摘にどう対応したかを添えて差分に集中させる：

```
Design Document を改訂しました（<パス>）。前回の指摘への対応は以下のとおりです:
- <指摘1> → <対応。採用/不採用と理由>
- <指摘2> → ...

改訂版を読み直し、次を返してください:
## 対応が不十分な点
## 改訂で新たに生じた懸念
## 残っている質問
## これ以上の大きな指摘がなければ「収束」と一言添えてください
```

送信は `--wait` で完了まで待つ：

```bash
herdr agent prompt "$NAME" "$PROMPT" --wait --timeout 600000
herdr agent read "$NAME" --source recent-unwrapped --lines 300
```

- 応答が `blocked` なら画面を読んでユーザーに提示し、指示に従って `herdr agent send-keys` 等で応答する（承認を自分で判断しない）
- `--lines` を増やしても応答の先頭が読めない場合のみ、レビュー結果を scratchpad ディレクトリの Markdown に書かせてそれを読む（herdr-subagent スキルのフォールバックと同じ）

### 3-2. 指摘を整理する

サブエージェントの出力をそのまま貼らず、**自分の評価を添えて**整理する。指摘は次の 3 つに分ける：

| 分類 | 扱い |
| --- | --- |
| **自分で直せる** | 記述の不足・曖昧さ・事実誤認（コードで確認できるもの）。ユーザーに聞かずに改訂する |
| **ユーザーの判断が必要** | スコープの増減、方針の選択、トレードオフの取り方、優先順位。選択肢と自分の推奨を添えてユーザーに聞く |
| **採用しない** | 的外れ、スコープ外、既にドキュメントで棄却済みの案。理由を添えて不採用とし、次ラウンドでサブエージェントにもそう伝える |

### 3-3. ユーザーに判断を仰ぐ

ラウンドごとに 1 回、以下の形でまとめて聞く（判断事項が無ければ聞かずに改訂へ進む）：

```
ラウンド <n>/<N> のレビュー結果（<KIND>/<MODEL>）

自分で直す: <件数> 件
  - <要約>
判断してほしい: <件数> 件
  1. <論点>
     選択肢: A) ... B) ...
     推奨: A（理由）
採用しない: <件数> 件
  - <要約>（理由）

1 の判断をお願いします。全部推奨どおりでよければ「推奨で」と言ってください。
```

- 質問は番号付きにし、まとめて答えられるようにする
- ユーザーが「もう十分」「終わって」と言ったらその時点でステップ4へ進む

### 3-4. 改訂する

- ドキュメントの**同じパスを上書き**する。別ファイルにしない
- design-doc スキルのフォーマット（4 セクションと下位見出し）を崩さない
- 採用しなかった指摘のうち、レビューで再び出そうなものは「設計判断 → 検討した代替案とその棄却理由」に理由付きで追記しておく。これが壁打ちの主要な成果物の 1 つ
- 改訂した箇所は把握しておき、最終報告で示す

### 収束の判定

次のいずれかで終了する：

- サブエージェントが「収束」と答えた、または重大な懸念が 0 件になった
- `--rounds` に達した
- ユーザーが終了を指示した

---

## ステップ4: 報告する（タブは残す）

最終版はステップ 3-4 で保存済み。返答は design-doc スキルと同じく **TL;DR で締める**。改訂した項目には「（更新）」を付ける。

```
✅ 壁打ち完了: <パス>（<n> ラウンド、レビュアー: <KIND>/<MODEL>）

主な改訂:
- <セクション>: <何をどう変えたか>
- ...

棄却して理由を記録した案:
- <案>（理由）

未解決（ユーザー判断待ち・保留）:
- <あれば>

壁打ち相手はタブ <TAB>（<NAME>）に残しています。
  続きを頼む   herdr agent prompt <NAME> "<テキスト>" --wait
  切り替える   herdr agent focus <NAME>
  閉じる       herdr tab close <TAB>

## TL;DR
- 何を変えるか: ...
- なぜ: ...（更新）
- どうやって: ...（更新）
- 判断のポイント: ...
- 確認したいこと: ...
```

- **タブは閉じない。** ユーザーが「閉じて」と言った場合のみ `herdr tab close "$TAB"`
- 閉じてよいのはこのスキルが作ったタブだけ。他のタブ・ペイン・ワークスペースに触らない

---

## 注意点

- **Herdr の外から操作しない**: `HERDR_ENV=1` の確認を省略しない
- **パスを推測しない**: ドキュメントのパスが無ければ聞く。ドキュメント以外のファイルを勝手に改訂しない
- **サブエージェントにファイルを書かせない**: 執筆権はホストにある。レビュアーには「ファイルは変更しない」と毎回伝える。サブエージェントが変更してしまった場合は `git diff` で確認してユーザーに報告する
- **ユーザーの判断を代行しない**: スコープ・方針・トレードオフの選択はユーザーに聞く。推奨は添えてよい
- **サブエージェントの出力を鵜呑みにしない**: 事実に関する指摘はコードで確認してから採用する。確認できない主張は「未確認」として扱う
- **ダイアログに勝手に答えない**: `blocked` になったら画面を読んでユーザーに提示する
- **1 タブ 1 エージェント、フォーカスを奪わない**: `--no-focus` を使い、タブ内で分割しない
- **同じ壁打ち相手を使い回す**: ラウンドごとにエージェントを立て直さない。会話の文脈がサブエージェント側に残っていることが壁打ちの前提
