# 設計判断スキル（design-policy）

設計案を5つの軸で定性的に評価し、意思決定のための判断材料を提示します。

## 入力

```
# Claude Code（ybaba プラグイン経由）
/ybaba:design-policy <設計案の説明やデザインドキュメント>

# OpenAI Codex CLI
$ybaba:design-policy <設計案の説明やデザインドキュメント>    # marketplace 経由のプラグイン
$design-policy <設計案の説明やデザインドキュメント>          # ~/.agents/skills/ fallback 導入時
```

## 理想像

このスキルが前提とする理想像：

> プロダクトを頭に思い描くと、0秒で非の打ちどころのない完璧なプロダクトが0秒でデプロイできる状態

5つの軸すべてが、この理想にどれだけ近づけるかを測る物差しとなります。

---

## 5つの評価軸

### 1. ビジネスの方向性

ビジネスが目指す方向と、この設計判断が整合しているか。

- 事業戦略やプロダクトビジョンとの一致度
- 市場・顧客のニーズへの対応
- 短期的な成果と中長期的な方向性のバランス

### 2. ソフトウェアの進化方向性

現在のソフトウェアが得意とするトレードオフ・優先しやすいトレードオフと、この設計判断の整合性。

- 現在のアーキテクチャが強いトレードオフは何か
- この設計判断はそのトレードオフの方向性を強化するか、変えるか
- ビジネスの方向性との整合性を強く意識する

### 3. ソフトウェアの進化適応度

ビジネスの潜在的・顕在的な要求に対して、ソフトウェアがどれだけ応えられているか。

- 現在のビジネス要求への充足度
- 潜在的な要求（まだ言語化されていないもの）への対応力
- CI/CDパイプラインなどの整備によるスピード感への対応
- 変化する要求に追随できる柔軟性

### 4. 不労所得度

売上に対して、かかる手間の比率はどうか。

- 一度作ったら手がかからない度合い
- 運用コスト・メンテナンスコストの低さ
- ただし、売上/手間の比率で評価する（大型受注で MRR が桁違いに上がるなら、手間がかかっても不労所得度は高い）
- 自動化・セルフサービス化の度合い

### 5. UI/UX, DevEx

ユーザー体験と開発者体験の両面。

- エンドユーザーの体験への影響
- 開発者の生産性・開発体験への影響
- 運用・デバッグのしやすさ
- オンボーディングの容易さ

---

## 評価の進め方

### ステップ1: 入力を受け取る

ユーザーから以下の2つを受け取ります：

1. **ビジネスの方向性**（毎回ユーザーが伝える）
2. **設計案**（以下のいずれかの形式）
   - 口頭での説明（「こういう設計にしようと思っている」）
   - デザインドキュメント（design-doc スキルの出力など）

情報が不足している場合は、ユーザーに質問して補完してください。特に以下が曖昧な場合は確認が必要です：

- ビジネスの方向性が伝えられていない
- 設計案の対象・範囲が不明確
- 「これから設計する案」なのか「既存の設計の振り返り」なのか判断できない

### ステップ2: 判断タイプを読み取る

設計案の内容から、判断タイプを文脈で読み取ります。明示的に分類する必要はありませんが、コメントの濃淡に反映させます。

**技術的な設計判断の場合**（例: 認証方式の変更、アーキテクチャの刷新）：
- **主軸**: ソフトウェアの進化方向性・進化適応度・UI/UX, DevEx
- **補助**: ビジネスの方向性・不労所得度

**プロダクト寄りの判断の場合**（例: 料金プランの追加、新機能の方針）：
- **主軸**: ビジネスの方向性・不労所得度
- **補助**: ソフトウェアの進化方向性・進化適応度・UI/UX, DevEx

ただし、この重みづけは固定ではなく、状況によって変わりえます。ユーザーとのすり合わせを大事にしてください。

### ステップ3: コードベースを調査する（必要に応じて）

既存の設計を振り返る場合や、設計案の影響範囲を把握するために：

- 関連するファイル・モジュールを特定する
- 現在の実装を把握する
- 依存関係や影響範囲を確認する

コードベースが関係ない場合はスキップしてください。

### ステップ4: 5軸で評価し出力する

以下のフォーマットで評価結果を出力してください。

---

## 出力フォーマット

```markdown
# 設計判断レビュー: <設計案のタイトル>

## ビジネスの方向性

<ビジネスの方向性との整合性について定性的にコメント>

## ソフトウェアの進化方向性

<現在のトレードオフとの整合性、ビジネス方向性との関係について定性的にコメント>

## ソフトウェアの進化適応度

<ビジネス要求への充足度、スピード感への対応について定性的にコメント>

## 不労所得度

<売上/手間の比率、運用コストについて定性的にコメント>

## UI/UX, DevEx

<ユーザー体験・開発者体験への影響について定性的にコメント>

## サマリー

### 強み
- <この設計案の強み1>
- <この設計案の強み2>

### 弱み・懸念点
- <この設計案の弱み・懸念点1>
- <この設計案の弱み・懸念点2>
```

### 書き方の注意点

- 主軸となる評価軸はより詳細に、補助的な軸は簡潔にコメントする（自然な濃淡をつける）
- 断定的な結論は出さない。判断材料の提示に徹する
- 意思決定はユーザーが行う。「こうすべき」ではなく「こういう側面がある」という表現を使う
- サマリーでは強み・弱みの両面を必ず提示する

---

## ステップ5: フィードバックと改善

評価を提示した後：

- ユーザーのフィードバックをもとに、評価の観点や濃淡を修正する
- 重みづけの認識にズレがあれば、すり合わせて再評価する
- 追加の情報が出てきた場合は、評価を更新する
