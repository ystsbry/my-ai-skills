# コンフリクト解消スキル（resolve-conflict）

main ブランチの最新を現在の作業ブランチにマージし、コンフリクトが発生した場合は両ブランチの意図を汲んで解消します。解消内容はレポートとして提示し、**ユーザーの承認を得てからコミット**します。

## 入力

```
# Claude Code（ybaba プラグイン経由）
/ybaba:resolve-conflict

# OpenAI Codex CLI
$ybaba:resolve-conflict    # marketplace 経由のプラグイン
$resolve-conflict          # ~/.agents/skills/ fallback 導入時
```

## 全体の流れ

1. 前提条件の確認（作業ツリーの状態・ブランチ）
2. main ブランチの最新化
3. マージ実行とコンフリクト解消
4. コンフリクト解消レポートの提示
5. ユーザー承認後にマージコミットを作成

---

## ステップ1: 前提条件を確認する

```bash
git status
git branch --show-current
```

以下を確認し、問題があれば**マージを開始する前に**ユーザーに伝えて指示を仰ぐ：

- **未コミットの変更がある場合**: マージ中に変更が失われる恐れがある。コミットするか `git stash` するかをユーザーに確認する。勝手に stash しない
- **現在のブランチが main（またはデフォルトブランチ）の場合**: マージ先として想定していない旨を伝え、対象ブランチを確認する
- **すでにマージ・リベースの途中の場合**（`git status` に `MERGING` や `rebase in progress` が出る）: 状態を報告し、続行・中断のどちらにするかユーザーに確認する

デフォルトブランチ名も確認する（main とは限らない）：

```bash
git remote show origin | grep 'HEAD branch'
```

以降、このスキル内の `main` はここで判明したデフォルトブランチ名に読み替える。

---

## ステップ2: main ブランチを最新化する

現在のブランチを離れずに main を最新化する：

```bash
git fetch origin main:main
```

- ローカル main に独自コミットがあり fast-forward できない場合はこのコマンドが失敗する。その場合は `git fetch origin` のみ実行し、以降のマージ元を `origin/main` に読み替える（ローカル main を強制的に書き換えない）
- fetch が認証エラー等で失敗した場合は、エラー内容を伝えてユーザーの対応を待つ

---

## ステップ3: マージを実行し、コンフリクトを解消する

```bash
git merge main --no-edit --no-ff --no-commit
```

`--no-commit` を付けることで、コンフリクトの有無に関わらず**コミット前にレポートを提示できる**状態にする。

### コンフリクトが発生しなかった場合

その旨を伝えたうえでステップ4のレポート（簡易版）に進む。

### コンフリクトが発生した場合

```bash
git status
git diff --name-only --diff-filter=U
```

でコンフリクトファイルの一覧を取得し、**1ファイルずつ**以下の手順で解消する：

#### 3-1. 両ブランチの変更意図を理解する

```bash
# コンフリクト箇所の3-way表示（base / ours / theirs）
git diff <file>

# 各ブランチでそのファイルに何をしたか
git log --oneline main -- <file> | head -20
git log --oneline HEAD -- <file> | head -20
```

必要に応じてコミットメッセージや周辺コードを読み、**なぜ両者がその変更をしたのか**を把握する。マーカーの機械的な削除だけで済ませない。

#### 3-2. 解消方針を決めて適用する

- **両方の変更を統合できる場合**（別々の機能追加など）: 両方の意図を活かして統合する
- **一方が他方を包含する場合**（同じバグの別修正など）: より完全な方を採用し、理由をレポートに書く
- **意図が衝突していて判断できない場合**（同じ挙動を別方向に変えているなど）: **勝手に判断せず**、その場でユーザーに確認する。確認できない事情がある場合は暫定的な選択をし、レポートで「要確認」として必ず明示する

解消後、コンフリクトマーカー（`<<<<<<<` `=======` `>>>>>>>`）が残っていないことを確認して stage する：

```bash
grep -n '<<<<<<<\|>>>>>>>' <file> || git add <file>
```

#### 3-3. 解消後の検証

すべてのファイルを解消したら、プロジェクトに応じた検証を行う：

- ビルド・型チェック・lint・テストのコマンドが判明している場合（CLAUDE.md、package.json、Makefile などから）は実行する
- 実行できない・時間がかかりすぎる場合は、レポートに「未検証」と明記する

---

## ステップ4: コンフリクト解消レポートを提示する

このスキルの `assets/conflict-report-template.md` を Read で読み込み、そのフォーマットに従ってレポートを作成し、コンソールに全文出力する。

- テンプレート内の `<...>` プレースホルダーを実際の内容に置き換える
- テンプレート内の HTML コメント（`<!-- ... -->`）は各セクションの書き方の指示であり、出力には含めない
- 「解消内容」のファイル数はコンフリクトファイル数に合わせて増減させる
- コンフリクトがなかった場合は「解消内容」を省略し、概要と取り込まれた変更のサマリー（`git diff --stat HEAD` など）のみの簡易レポートとする
- レポートは GitHub の PR コメントにそのまま投稿できる文面にする。「次のアクション」のような会話向けの文言はレポート本文に含めず、レポート全文を出力した**後に**、コンソール上で「問題がなければマージコミットを作成します。修正が必要な箇所があれば指摘してください」とユーザーに確認する

レポートは**コンソールに出力するだけ**でよい。ファイルには保存しない（そのまま PR コメントに貼れる形で出力することが目的のため）。

---

## ステップ5: 承認を得てコミットする

レポート提示後、**ユーザーの返答を待つ**。勝手にコミットしない。

### 問題ないと言われた場合

```bash
git commit --no-edit
```

（`--no-edit` でデフォルトのマージコミットメッセージを使う。ユーザーがメッセージを指定した場合はそれに従う）

コミット後、SHA を報告する。**push はユーザーが明示的に指示した場合のみ**行う。

### 修正を求められた場合

指摘された箇所を修正して `git add` し、レポートの該当箇所を更新して全文を再提示する。

### マージ自体を中止したいと言われた場合

```bash
git merge --abort
```

で作業ブランチをマージ前の状態に戻し、その旨を報告する。

---

## 注意点

- **破壊的な操作をしない**: `git checkout --ours/--theirs` の一括適用、`git reset --hard`、force push はユーザーの明示的な指示なしに実行しない
- コンフリクト解消は「マーカーを消す作業」ではなく「両ブランチの意図を統合する作業」。必ず両側の変更理由を理解してから解消する
- lock ファイル（`package-lock.json`、`Cargo.lock` など）のコンフリクトは、手動マージせず**元ファイル解消後に再生成**する（例: `npm install`）。再生成コマンドが不明な場合はユーザーに確認する
- 解消の途中でユーザーから中断・方針変更の指示があった場合は、現在の状態（どこまで解消済みか）を明確に伝えてから従う
