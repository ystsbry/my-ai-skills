# 調査ドキュメントサイト生成・保守スキル（doc-site）

調査・設計・検討の結果を、リポジトリの `.docs/` 配下に**マークダウン群と単一マルチページHTMLの二重形式**で出力し、以降の編集・改訂を両形式の整合を保ちながら行います。

## 入力

```
# Claude Code（ybaba プラグイン経由）
/ybaba:doc-site <テーマ名や、ドキュメント化したい内容の指示>

# OpenAI Codex CLI
$ybaba:doc-site <テーマ名や、ドキュメント化したい内容の指示>    # marketplace 経由のプラグイン
$doc-site <テーマ名や、ドキュメント化したい内容の指示>          # ~/.agents/skills/ fallback 導入時
```

素材は、ここまでの会話内容・指定されたファイル・調査結果など何でも受け取れます。

---

## 出力の標準構成

```
.docs/<テーマ>/            # バージョン管理する場合は .docs/<テーマ>/v<n>/
├── 00_tldr.md            # TL;DR（全体要約。他の md 完成後に作る）
├── 01_<トピック>.md       # テーマ別マークダウン（01, 02, ... の連番）
├── 02_<トピック>.md
├── ...
└── index.html            # 全ページを収めた単一のマルチページHTML
```

- **テーマ名・ファイル名はケバブケースの英語**、内容は日本語で書く
- ディレクトリの切り方（バージョンありなし含む）は、指示がなければ提案して確認する
- 既に `.docs/<テーマ>/` が存在する場合は中身を読んでから、新規作成ではなく更新として扱う

---

## HTML の体裁規約（毎回必ず守る）

1. **単一ファイル・マルチページ**: HTML は必ず1ファイル。md 1本 = 1ページとし、JavaScript でページを切り替える。ページごとにファイルを分けない
2. **サイドバーナビゲーション**: 左にページ一覧のサイドバーを固定表示。現在ページをハイライトする
3. **URL を変えないページ切り替え**: ページ切り替えは表示の切り替えのみで行い、URL を一切変化させない。`href="#page-id"` のようなハッシュリンクや `location.hash`・History API（`pushState` / `replaceState`）は使わない。ナビゲーションは `<button>` か `href` なしの要素（または `preventDefault()` 済みのリンク）で実装し、JS の状態変数と CSS の表示切り替え（クラス付け外し）だけでページを選択する
4. **トグル**: 補足・詳細・長いコード/SQL は `<details><summary>` のトグルに入れる
5. **図解**: 構成・フロー・関係性は文章だけにせず、SVG またはスタイル付き div で図解する
6. **配色コントラスト**: 文字色と背景色のコントラストを必ず確保する。白背景に白系・薄いグレーの文字は禁止。バッジや強調色の上の文字も同様に確認する
7. **自己完結**: 外部 CDN・外部フォント・外部画像を参照しない。CSS/JS はすべてインライン
8. **先頭ページは TL;DR**: サイドバーの最初は TL;DR ページにする

## 生成の進め方

### ステップ1: 構成を決める

素材（会話・ファイル・調査結果）から、ページ構成（md の分割単位）を決めてユーザーに提示する。項目指定があればそれに従う。曖昧なら構成案を示して確認してから書き始める。

### ステップ2: マークダウン群を書く

各トピックの md を書く。書き方の規約：

- 見出し階層は `#`（ページタイトル）→ `##` → `###` まで
- 事実と推測を区別する。ソースコードから確認した事実は根拠（ファイルパス等）を添え、未確認・要確認の箇所には **⚠️要確認** マーカーを付ける
- 表で整理できるもの（比較・一覧・入出力）は表にする

### ステップ3: TL;DR を書く

全 md が揃ってから `00_tldr.md` を書く。各トピックの結論だけを拾い、1ページで全体像がわかる要約にする。

### ステップ4: HTML を生成する

上記の体裁規約に従い、全 md の内容を `index.html` に変換する。md の単なる転記ではなく、図解・トグル・表を活かした「人が読みやすい」形に再構成する。

### ステップ5: 閲覧方法を案内する

生成完了後、必ず閲覧方法を案内する。WSL 環境では：

```bash
# Windows のブラウザで開く
wslview .docs/<テーマ>/index.html
# または
explorer.exe "$(wslpath -w .docs/<テーマ>/index.html)"
```

`file:///` 形式のパス（`wslpath -w` の結果を `file:///` に変換したもの）も併記する。

## 編集・保守のルール（生成後の依頼への対応）

### 同期反映（最重要）

**md と HTML は常に同時に更新する。** 「この項を削除して」「〜を追記して」という指示を受けたら：

1. 該当する md を修正する
2. `index.html` の対応ページも同じ内容に修正する（サイドバーの表記・TL;DR への影響も確認）
3. 修正が他ページに波及する場合（用語変更・前提の変更など）は、波及先も洗い出して反映する

片方だけの更新は、明示的に「md だけ」「html だけ」と言われた場合を除き行わない。

### ⚠️要確認マーカーの解消

ユーザーから確認結果が共有されたら、該当箇所のマーカーを外して確定情報に書き換え、関連ページにも反映する。

---

## バージョン改訂（v1 → v2）

新しい情報（会議メモ・追加調査など）を受けて改訂版を作る場合：

1. **照合**: 新情報と現行版を突き合わせ、「どのページにどんな変更が入るか」の差分提案を先に提示する
2. **確認**: ユーザーの合意を得てから v(n+1) を作成する
3. **単体成立**: v(n+1) は「v(n) からの差分」ではなく、**それ単体で読んで成立する完全版**として書く。md 群・TL;DR・HTML をフルセットで生成する
4. 旧バージョンのディレクトリはそのまま残す（削除しない）
